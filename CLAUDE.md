# ArBeHarness

A high-performance, model-agnostic Rust agent harness with a lightweight TUI. The harness (core runtime, providers, memory, tools, skills, hooks, MCP) is the product; the TUI is a thin, decoupled visualization/control layer on top of it.

Full specs live in `/docs` — read them before making architectural decisions, don't re-derive from scratch:
- `docs/v1-overall-design.md` — architecture, workspace layout, module responsibilities
- `docs/v1-harness-spec.md` — functional/non-functional requirements, core trait signatures, persistence + error taxonomy
- `docs/v1-implementation-plan.md` — phase-by-phase delivery plan, per-crate backlog, config schema, risk register
- `docs/v1-tui-spec.md` — TUI requirements, event contract, keybindings
- `docs/user-guide.md` — the end-user guide (keep in sync with behavior, see Working conventions)
- `docs/v2-implementation-plan.md` — **the active plan.** Phased v2 roadmap (P0–P7) with a status table and per-task checkboxes; read this first to know what's in progress and what's next, and keep it updated as work lands
- `docs/v2-status.md` — **honest v2 acceptance checklist**: every exit criterion with its evidence, and what's still open (its **Pending work** section is the single list of open items — keep it current). Update it when a criterion's status changes; never mark something met that wasn't verified
- `docs/v1-status.md` — frozen v1 acceptance-criteria checklist (historical; superseded by the v2 plan's status table)
- `docs/user-guide.md` — **end-user documentation** (CLI args, env vars, providers, keybindings, chat commands, tools/approvals, instruction & skill files, sessions, `~/.arbe/` layout, file formats, logs). See the doc-maintenance rule under "Working conventions".

## Current state

Phase 0 (workspace + CI skeleton) is done: the `crates/arbe-*` workspace exists, each crate compiles, and each non-`arbe-core` crate defines only its shared trait/type contract from the spec docs (no behavior yet — that's what each later phase fills in). `arbe-core` has real domain types (`SessionMeta`, `Turn`, `Message`, `ToolInvocation`), the `LoopPhase` state enum, the `RuntimeEvent` contract (clients act through `Agent`'s methods; the unused `RuntimeCommand` enum was removed), and the error taxonomy. `arbe-runtime` has a working `EventBus` (tokio broadcast). `arbe-storage` has `~/.arbe/` path resolution only — no read/write yet. CI matrix (fmt/clippy -D warnings/test on ubuntu/macos/windows) is in `.github/workflows/ci.yml`.

Phase 1 (loop skeleton + persistence) is done: `arbe_core::LoopMachine` enforces the legal `LoopPhase` transition graph from the design doc (including the tool-call and direct-response branches); `arbe_storage::SessionStore` persists `meta.json` (atomic write, fsynced, keeps the replaced file's permissions), append-only `turns.jsonl`/`in_flight.jsonl`/`compactions.jsonl` (`atomic::append_line` fsyncs and cuts off a torn last line before appending, so a crash mid-append can't later make the log unreadable), and supports create/load/resume/list, with tests covering forced-interruption recovery. `SessionStore` only has `with_root` (no constructor reads `ARBE_HOME`); likewise `arbe_storage::paths` keeps only `arbe_home()` (for entry points) and `*_at(root)` helpers.

Phase 2 (provider abstraction + first adapters) is done — and its contract was replaced in v2 P1, see "v2 core contract" below. `arbe-providers` has `OpenAiProvider` and `OllamaProvider`, built through `ProviderRegistry` so switching providers is a config change. HTTP/parsing logic is split into pure, network-free functions (`build_request_body`, `translate_chunk`/`translate_line`, `SseDecoder`, `map_http_error`) so they're unit-testable without a live API or mock server — there is currently no integration test that hits a real OpenAI/Ollama endpoint.

Phase 3 (context & memory v1) is done: `arbe-memory` has a deterministic token estimator (`estimate_tokens`, ~4 chars/token — not a real tokenizer, but reproducible without a provider-specific one), the two strategies (`TruncationStrategy`, and `TruncateWithNoticeStrategy` — the same trimming plus a notice of what was left out, used by `memory_strategy = "compact_summary"` alongside the runtime's model-written compaction) sharing one selection rule (`truncation::select_kept`: pinned turns always kept, most recent unpinned kept until budget runs out), and a `ContextPipeline` assembling system/global/skill instructions → history → memory notes → user turn per overall design §5.2, deducting fixed costs from the budget before handing the remainder to the strategy. Persistent memory files are read and appended by `arbe-runtime`'s `agent/memory.rs` (`<home>/memory/global/memory.md`, `<home>/memory/projects/<id>/memory.md`); a missing file is `None`, not an error.

Phase 4 (tools + approval gate) is done: `arbe-tools::ToolRegistry` maps tool name -> `Arc<dyn ToolExecutor>` (this is also where MCP-exposed tools land later, per overall design §4.4 — same registry, no separate MCP path). `StandardApprovalPolicy` implements the four harness-spec FR-4 modes against a `PolicyOutcome` (`AutoApprove`/`AutoDeny`/`RequiresPrompt`) — deliberately not `arbe_core::ApprovalDecision` directly, since only a human decision can resolve `RequiresPrompt` and the policy alone can't produce one. `gate::execute_gated` is the single choke point: it looks up the tool, asks the policy, and — if the policy says `RequiresPrompt` and no `human_decision` was passed — returns `GatedOutcome::PendingApproval` instead of executing, so the runtime loop can pause at `LoopPhase::ToolApproval` and re-call it with the human's decision once one arrives. No code path in this crate reaches `ToolExecutor::execute` except through `execute_gated`.

Phase 5 (skills, hooks, MCP baseline) is done:
- `arbe-skills` parses `---`-delimited frontmatter manifests (`name`/`description`/`tags` + body instructions), loads a scope directory's `*.md` files and `<folder>/SKILL.md` skill folders, no deeper (missing dir → empty, not an error; the frontmatter parser reads top-level keys only, with quotes and `|`/`>` blocks, so other agents' `SKILL.md` files parse); the runtime reads `~/.arbe/skills`, `<project>/.arbe/skills` and `<project>/.agents/skills`, and `merge_skills` applies project-local > global precedence on name collision (the spec's session-local scope isn't built).
- `arbe-hooks::HookRegistry` runs each phase's hooks in order, threading a transformable JSON payload through the chain; each hook runs inside its own `tokio::spawn` + `tokio::time::timeout`, so a panicking or hanging hook is isolated (skipped, previous payload kept) instead of taking down the turn or the other hooks.
- `arbe-mcp` has a real stdio JSON-RPC client (`McpClient`: `initialize` handshake, `tools/list`, `tools/call`) and its tools are bridged into `arbe_tools::ToolRegistry` as `server__tool` (sanitized to `[A-Za-z0-9_-]`, ≤ 64 chars; a name that's taken gets a `_2`, `_3`, … suffix via `unique_tool_name`, and the runtime's `RegistrySink` records which names belong to which server, so a refresh replaces exactly those). Servers are configured under `[mcp.servers.<name>]` in `config.toml` (see "v2 MCP"). The JSON-RPC framing (`protocol.rs`: request/notification building, response parsing incl. server-side errors and id mismatches) is fully unit-tested without any process; `McpClient` itself has **no live-process integration test** — there's no reference MCP server available in this environment/CI to spawn, so the process-spawning + stdio plumbing is straightforward tokio boilerplate that's reviewed but not exercised by an automated test. Flag this if a real MCP server becomes available to test against.

Phase 6 (TUI MVP) is done:
- `arbe-runtime::Agent` (`crates/arbe-runtime/src/agent/`) was rewritten in v2 P3 — see "v2 agent loop" below for how it works now.
- `arbe-tui` uses ratatui + crossterm: 3-region layout (status header incl. profile/provider/model/session id/phase/context estimate/session tokens used, scrollable role-colored transcript, input bar with hints) plus a tool-approval modal (`y`/`n`/`a`/`d`; `Esc` cancels the turn). It holds the agent as a plain `Arc<Agent>`; turns and `/tool` calls run on spawned tasks, and everything they do arrives as `RuntimeEvent`s, so the render loop never blocks. `Esc` while working cancels the turn.
- `arbe-tui` depends only on `arbe-runtime`, reaching `arbe_core`/`arbe_tools` types through `arbe_runtime`'s re-exports (not direct deps) — preserves the core/tui separation rule.
- Verified for real: `cargo run --release` renders the actual layout in a terminal (header, transcript box, input box with correct hint text) — confirmed via a captured run, not just a successful `cargo build`. Full interactive verification (typing, streaming a real reply, the approval modal) needs a human at a real terminal — this environment has no interactive TTY to drive keypresses through.
- `RuntimeConfig::from_env()` defaults to `ollama` with `qwen2.5-coder:7b` for the coding profile and `llama3.2:3b` for the general prompt (no API key needed to launch; Ollama tool calling is on, and a model without tool support is detected and retried without tools); set `ARBE_PROVIDER=openai` + `OPENAI_API_KEY` to use OpenAI instead (its reasoning-family models also need `max_completion_tokens` instead of `max_tokens` and reject non-default `temperature` — both handled). `RuntimeConfig::project_dir` (`ARBE_WORKDIR`/`--workdir`, default: cwd) is the repo/project the agent works on — distinct from `ARBE_HOME`/`--dev-home`, a **dev/test-only** knob that relocates the harness's own storage root.

Phase 7 (hardening) is done: cross-crate integration coverage was added at the `Agent` level (`crates/arbe-runtime/src/agent.rs` tests) — session recovery after a forced interruption (drop mid-session, reconstruct from disk, confirm history/next-turn-index/continued-append all correct) and memory-strategy-swap-via-config-alone (same history/budget, different strategy, visibly different output). Skills are now wired into `Agent` (global scope loaded from `~/.arbe/skills/` and folded into the context pipeline), and hooks now run at `BeforeModelCall`/`AfterModelCall`/`OnTurnComplete` (previously only the last). `docs/v1-status.md` is an honest pass/fail against every acceptance criterion in the harness and TUI specs — nothing was marked done that isn't. Benchmarks (implementation plan's "turn latency/stream smoothness" deliverable) were deliberately **not** added — no representative hardware/load profile to benchmark against yet, and a fake benchmark would be worse than none.

**Builtin tools** (`crates/arbe-tools/src/builtin/`, added after Phase 7): a deliberately small, high-quality set — `read_file`, `write_file`, `edit_file`, `list_dir`, `glob`, `grep`, `execute`, `todo_write` — each in its own file, registered automatically by `Agent::assemble` against `RuntimeConfig::project_dir`. Every filesystem tool is sandboxed through `path_guard::resolve_within_root` (lexical `.`/`..` resolution + a component-wise `starts_with` check — heavily unit-tested, since every other tool's safety depends on it). `write_file`/`edit_file` reuse `arbe_storage::atomic::write_atomic` for crash-safe writes. `glob`/`grep` use `walkdir`+`globset`/`regex` (skip `.git`/`target`/`node_modules`/`.venv` by convention) and cap output size so a broad query can't flood context. `execute` is the one tool that can't be sandboxed the same way — arbitrary shell execution, always gated. `todo_write` is the one tool with in-memory state instead of a filesystem root (`Mutex<Vec<TodoItem>>`, one instance per `Agent`/session): each call replaces the whole list (not a diff), rejects more than one `in_progress` item, empty content, and more than 200 items. Each tool describes itself (`ToolExecutor::description`, schema derived from its `Args`), declares its `default_risk`, and says what its rule subject is (`subject` + `subject_kind`: `Path`, `ShellCommand` or `Other` — allow rules never stretch `*` over shell operators in a `ShellCommand`, and nested instruction files only follow `Path` subjects). `register_all` is the list of builtins; `ToolRegistry::names()` is the source of truth.

**System prompt composition** (added after builtin tools, see `docs/tmp/system-prompt.md`): `crate::system_prompt::render_system_prompt` in `arbe-runtime` combines a hardcoded template (temporary wording — the `{global_instructions}`/`{project_instructions}` substitution contract is the real deliverable) with two file sources read via `arbe-storage`: `arbe_storage::instructions::read_global_instructions_at(home)` (`<home>/instructions/agent.md`, machine-wide) and `read_project_instructions` (`<project_dir>/agent.md`, falling back to `CLAUDE.md`; no parent-directory walk). Each section is capped at 8,000 chars before substitution, since `ContextPipeline` charges system instructions as a fixed cost against the token budget ahead of history. Rendered fresh into `ContextPipeline.system_instructions` on *every* `submit_message` call (not cached at `Agent::assemble`), so edits to either file take effect on the next turn without restarting the session — proven by an `Agent`-level test that edits `agent.md` mid-session and checks the next turn's rendered prompt picks it up. This replaced `RuntimeConfig::system_instructions`, which is now redundant.

`docs/todo.md` tracks feature gaps identified by comparing our system prompt against a reference agent's (nested project instruction files, plan mode, `ask_user_question`, background tool execution, subagents, MCP schema-lookup-before-use, rich output formatting conventions) — a punch list, not a commitment.

**v2 core contract** (v2 plan P1, done):
- `arbe_core::Message` is a list of typed `ContentBlock`s (`Text`, `Image`, `ToolUse`, `ToolResult`, `Thinking`, `Opaque`), not a string. Use `Message::new(role, text)`, `text()`, `tool_uses()`, `tool_result(...)`; serde still accepts v1's plain-string `content`.
- `ModelProvider` has one method, `stream(req, cancel) -> ProviderStream` of typed `ProviderEvent`s; `arbe_providers::infer()` folds the same stream through the pure `ResponseAccumulator` for non-streaming callers. Adapters only translate wire format → events; cancellation (`http::cancellable`) and status/`Retry-After` mapping (`http::send`) are shared. `capabilities(model)` is per model.
- `ToolExecutor::execute(invocation, &ToolContext)` — `ToolContext` carries a `CancellationToken` and optional progress sink; `execute` kills its whole process tree on cancel/timeout. **`ToolContext` is issued only by the gate** (`Authorized::execute(ToolRun { cancel, progress })`; private field, no `Default`/`Clone`), so harness code can't run a tool without approval — it doesn't compile. Unit tests of a single executor use `ToolContext::for_testing()` (the `arbe-tools/testing` feature, enabled only in `[dev-dependencies]`; `cargo tree -e features -p arbeharness` must not show it) or, inside `arbe-tools`, `ExecuteWithDefaultContext::execute_default`.
- `Turn` (schema v2) stores the turn's full `messages` list plus `usage`/`stop_reason`; v1 records are converted on read. `SessionMeta` has cumulative `usage` and a `title`.
- `EventBus` publishes `EventEnvelope { seq, event }` (gap-free `seq`). New events: `ThinkingDelta`, `ToolUseStarted`, `ToolUseInputDelta`, `ToolProgress`, `UsageUpdated`, `CompactionPerformed`, `TurnCancelled`. The TUI gives each session its own bus (a replaced session's late events can't reach the new transcript); a client that missed events (a `seq` gap) asks `Agent::pending_approvals()`/`pending_questions()` (headless: `session/pending`) what's still waiting on it.
- Errors: `ProviderError` gained `RateLimit { retry_after }`, `Overloaded`, `ContextLengthExceeded`, `Unreachable` (not retried), `Network`, `Cancelled` (+ `is_retryable()`); `HarnessError` gained `Internal`/`Cancelled`; `UserFacing` is implemented.

**v2 provider layer** (v2 plan P2, implemented; live runs pending):
- Providers: `openai`, `openai_compatible` (any Chat Completions server; `base_url` required, key optional), `anthropic`, `ollama` — built via `ProviderRegistry::with_builtins().build(id, ProviderSettings)`. Keys: `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`, falling back to `ARBE_API_KEY`.
- `ModelCatalog` gives per-model capabilities (context window, vision, thinking) by longest name prefix; adapters answer `capabilities(model)` from it.
- The agent calls providers through `stream_with_retry` (`RetryPolicy`; retries only before the first event; each retry → `RuntimeEvent::ProviderRetrying`). `http::client()` has connect + idle-read timeouts.
- `TokenCalibration` (arbe-memory) corrects the chars/4 estimate from reported input tokens; the context budget and the displayed estimate go through it.
- Live smoke tests: `cargo test -p arbe-providers --test live -- --ignored --nocapture` (each provider skips without credentials). Stream fixtures in unit tests are hand-written from documented formats, not captured traffic. End-to-end: `cargo test -p arbe-runtime --test live_agent -- --ignored --nocapture` runs 12 per-feature agent tests against a real model — set `ARBE_LIVE_COMPAT_BASE_URL`/`_MODEL`/`_API_KEY` for any OpenAI-compatible server (validated on xAI `grok-4.7`: 12/12) or `ARBE_LIVE_OLLAMA=1` for local Ollama. The same variables drive the `openai_compatible_live` provider test and the live test in `tests/cli.rs`. Small open models sometimes write tool calls as text — `arbe-providers/src/text_tool_calls.rs` recognizes a reply that is *only* calls to offered tools (wired into Ollama; reusable for `openai_compatible`).
- Env knobs added: `ARBE_MAX_RETRIES`, `ARBE_THINKING_BUDGET`, `ARBE_HTTP_HEADERS`, `ARBE_CONTEXT_BUDGET`, `ARBE_MAX_TOOL_ROUNDS`.

**v2 config & profiles** (v2 plan P4.1–P4.3): `RuntimeConfig::load()` layers defaults → built-in profile → `~/.arbe/config/config.toml` → `<workdir>/.arbe/config.toml` → `[profiles.<name>]` sections → `ARBE_*` env (CLI flags set env). Use `RuntimeConfig::load_from(files, &env_fn, project_dir)` in tests (env as a function — never mutate process env) or `RuntimeConfig::defaults(dir)` for a plain struct. Profiles carry a tool allow-set (enforced via `ToolRegistry::retain`) and a `PromptTemplate`. **Trust:** project config comes with whatever repo is opened, so unless the global config lists the project in `trusted_projects`, `Layer::strip_sensitive` drops its provider endpoint/key-var/key-command/headers, `[approval]`, `[mcp]`, `[web]`, hook commands and a `prompt` template *file* (the built-in `coding`/`general` stay allowed) — the same in its profiles — with a warning. Any new config key that can leak secrets or local files, weaken approvals, or run programs must be added there. **Provider settings go together:** a layer (or `ARBE_PROVIDER`) that selects a *different* provider drops the lower layers' model/base_url/headers/key var/key command (`RuntimeConfig::switch_provider`), so a key never goes to another provider's address. Built-in profiles are data (`BUILTIN_PROFILES`) applied like a `[profiles.x]` section, after the files' top level. Use `load_from_sources(global, project, env, dir)` to test this. Tool specs come from `ToolExecutor::description()` (`ToolDescription::from_args::<Args>` via schemars — put model-facing docs on the `Args` fields) and `ToolRegistry::specs()`.

**v2 permissions & secrets** (v2 plan P4.8/P4.9): approval lists are `arbe_tools::ToolRule`s (`tool` / `tool(pattern)`, `*` crosses `/`), matched against `ToolExecutor::subject` (path or command line) — a new side-effecting tool should implement `subject`. Deny rules apply in every mode; high-risk calls auto-approve only via a rule with a pattern; a session approval of a high-risk call is an exact, *literal* rule. `arbe_runtime::redact::Redactor` scrubs known secrets from tool output (model input, `turns.jsonl`, events) — anything new that surfaces tool output must go through it.

**v2 MCP** (v2 plan P4.4/P4.5, `crates/arbe-mcp/`): `McpClient` routes responses by id (concurrent calls), over `stdio.rs` or `http.rs` (streamable HTTP); `McpServer` reconnects a closed client on next use; `McpManager::connect_all` registers tools through a `ToolSink` (the runtime's `RegistrySink`) and `refresh_changed` handles `tools/list_changed`. Configured as `[mcp.servers.<name>]` in `config.toml`; the agent connects them in the background (`McpServerConnected`/`McpServerFailed`). Tests: `tests/client.rs` against the `mcp-fixture-server` bin (use `env!("CARGO_BIN_EXE_mcp-fixture-server")`); `--ignored` tests hit the official `server-everything` via npx.

**v2 agent loop** (v2 plan P3, `crates/arbe-runtime/src/agent/`):
- `Agent`'s methods all take `&self`; share it as `Arc<Agent>` with no outer lock. `submit_message` runs one turn (a second concurrent one → `HarnessError::Busy`); `cancel_turn()` and `supply_tool_decision(id, decision)` work *during* a turn; `invoke_tool(name, args)` is the manual `/tool` path and goes through exactly the same gated code as a model call.
- Modules: `mod.rs` (session state + API), `turn.rs` (turn runner: streaming rounds, loop guards, persistence), `tools.rs` (one round of tool calls), `hooks.rs` (typed hook payloads), `approvals.rs` (decision mailbox), `tests.rs`.
- Tool rounds: hooks + approval run one call at a time in the model's order (a `BeforeToolExecute` hook can rewrite arguments or `veto` *before* the human sees the call); approved calls then run concurrently unless `ToolExecutor::parallel_safe()` is false (`write_file`, `edit_file`, `execute`, `todo_write`). Results go back in the model's order as one tool message, truncated head+tail to `max_tool_output_chars`. Denials, vetoes and tool errors are results the model sees, not turn failures. The gate is split: `arbe_tools::authorize` → `Authorized` (only the gate can create one) → `Authorized::execute`.
- Persistence: every message of a turn is appended to `in_flight.jsonl` as it's produced and the full trace goes to `turns.jsonl` on commit (then the in-flight log is cleared). `Agent::resume` recovers a leftover in-flight turn as `StopReason::Interrupted`. Unanswered tool calls are always closed with error results (`turn::close_dangling_tool_uses`, matched by position since some servers reuse call ids). The full trace is replayed into later turns; `arbe-memory` trims history whole turns at a time (condensing a too-big turn to question + answer) so call/result pairs never split.
- Loop guards end the turn with an explicit `StopReason` (on `TurnCompleted`): `ToolRoundLimit`, `TurnTokenLimit` (`ARBE_MAX_TURN_TOKENS`), `RepeatedToolCall` (3 identical rounds). Cancellation keeps partial output and persists the turn as `Cancelled`; a failed turn is kept only if it did more than receive the question.
- Turn-end check (verify-on-stop): when the model answers and a non-`read_only` tool ran since the last check (`Lineage::changed`, so subagents' calls count), the top-level agent runs `before_turn_end` hooks; a blocking failure or `"continue"` output is recorded as a `[harness]` user message and the loop goes on (`InterpretOutput → PostToolReflection → ModelInference`), at most `MAX_TURN_END_CHECKS` times. It's a hook, not a built-in check, so it fits non-coding work too.

**v2 embedding & CLI** (v2 plan P6.1/P6.2): `arbe_runtime::harness` is the public facade (`Harness::builder()...build()` → `Session::send` → `Turn::next_event`/`finish`); `src/main.rs` + `src/cli.rs` (strict hand-rolled parser — unknown flags are errors) + `src/print.rs` (`--print` headless one-shot) + `src/headless.rs` (`--headless` JSON-RPC 2.0 over stdio; one forwarder task per session writes events *and* turn responses, which is what guarantees a response follows its turn's events — keep it that way) are built on it, and the TUI takes a `Harness` for new/resumed sessions. `RuntimeConfig.home` is the harness home for everything the agent reads/writes — don't call `arbe_storage::paths::arbe_home()` from agent code. Subagents (`agent/subagent.rs`, the `task` tool): a child `Agent` shares the parent tree's `Lineage` — one `ToolDecisions` mailbox and `SessionApprovals` (so approvals route through the top-level agent), a concurrency semaphore, and a depth — and its events reach the parent wrapped in `RuntimeEvent::SubagentEvent` (use `innermost()` in consumers; only depth-0 `TurnCompleted` ends a top-level turn). `meta.json` carries `workdir`/`branch`/`activity`/`pid` (and `parent` for subagents) for other programs to read (see the user guide's File formats); keep them accurate when touching session lifecycle (`mark_open`, `set_activity`, `close`). Binary tests: `tests/cli.rs`.

**v2 P6 additions:** `ask_user` (`agent/ask.rs`; a `QuestionMailbox` shared through the subagent `Lineage` like approval decisions; `Agent::answer_question`); background processes (`arbe-tools/src/builtin/processes.rs`, a per-registry `ProcessTable` shared by `execute`/`process_output`/`process_kill`); web tools (`builtin/web.rs`; `[web.search]` is trust-stripped from project config and its key redacted); observability (the *binary* installs the log subscriber in `src/main.rs` — the library never does; spans `turn` → `tool`; `Pricing`/`cost_usd`). Two `ToolExecutor` hooks to know: `requires_approval()` (false = skip the human prompt, but still through the gate — deny rules and dry-run apply) and `close()` (called by `Agent::close` via `ToolRegistry::close_all`: release anything that must not outlive the session). Commits are gated on the full suite passing.

**Session modes** (v2 plan P6.6, `agent/modes.rs`): a mode (`default`, `plan`) is a `ModeSpec` — tool access (`All` or `ReadOnly`, via `ToolExecutor::read_only()`), prompt instructions, and an optional exit tool the user must approve (`exit_plan_mode`). The mode is shared through the subagent `Lineage`; tools are filtered per round (`Agent::offered_tool_specs`) and a disallowed call is refused in `tools::approve_call` before hooks/approval. A new read-only tool must override `read_only()` or plan mode won't offer it; a tool with side effects must not.

**Context accounting** (v2 plan P5.7): every model round's request is measured whole — `ContextBreakdown` by source (system prompt, instruction files, skills, memory, summary, tool definitions, history / current turn by content kind) — and published calibrated as `RuntimeEvent::ContextUpdated`; `Agent::context_usage()` returns the latest. Anything new that goes into a request (a new preamble section, extra per-request payload) must be counted there too, or the breakdown stops adding up to what's sent — `the_breakdown_accounts_for_every_message_by_source` checks the sum.

v1 is a real, working, tested product core — not a finished release. Work now follows `docs/v2-implementation-plan.md`; its status table is the source of truth for what's done.

## Non-negotiable architecture rules

- `arbe-core` must never depend on `arbe-tui`. The TUI consumes runtime events/commands only — no agent decision logic in the TUI crate.
- Memory strategies, provider adapters, skill registries, tool executors, and approval policies are all trait-based and swappable via config, not code changes.
- Tool execution always goes through the approval gate (`ApprovalPolicy`) — no side-effecting tool call bypasses it, even in early scaffolding/test code.
- All persistent state lives under `~/.arbe/` (config, sessions, memory, skills, instructions, mcp, logs). Use atomic writes (temp file + rename) for config/metadata; JSONL append-only for turns/events.
- Cross-platform from day one: avoid OS-specific path/process assumptions (Linux/macOS/Windows CI matrix is part of Definition of Done).

## Working conventions

- Prefer adding to the existing crate/module structure implied by the current phase over introducing new crates ahead of schedule.
- Config-first: new strategies/behaviors should be selectable via config (see the `[profile]`/`[memory]`/`[tools]`/`[hooks]`/`[mcp]` schema draft in the implementation plan), not hardcoded branches.
- When a phase's exit criteria aren't met yet, say so explicitly rather than marking it done.
- `docs/user-guide.md` describes what the harness does *today* for end users. Any change to CLI flags, env vars, keybindings, chat commands, tools, file locations/formats, or visible behavior updates it in the same commit; features that exist but aren't connected go under its "Not yet active" section.
- **Keep `docs/user-guide.md` in sync — part of Definition of Done.** Any change that affects what an end user sees or configures must update the guide in the same change: CLI flags (`src/main.rs`), env vars/defaults (`RuntimeConfig::from_env`), providers/default models/context windows (`arbe-providers` registry/catalog), keybindings or chat commands (`arbe-tui`), builtin tools, their args, limits, or risk levels (`arbe-tools::builtin`), approval behavior, files read/written under `~/.arbe/` or the workdir, and on-disk formats (`meta.json`, `turns.jsonl`, skill/instruction files). When a feature listed in the guide's "Not yet active" table gets wired up, move it into the relevant section. Describe only what actually works — never document planned behavior as current.
