# OpenClaw (general personal agent runtime)

Inventoried product: the OpenClaw Foundation project documented at [docs.openclaw.ai](https://docs.openclaw.ai/) and developed at [github.com/openclaw/openclaw](https://github.com/openclaw/openclaw/tree/7b624e9de25bc66c97166071c8d05f055d82ec54). Chosen because that is the self-hosted gateway the official docs, lore, and architecture pages describe, and the same pages name the earlier shells (Warelay, Clawdbot, Moltbot). Not inventoried: community mirrors (for example clawdocs.org), the .NET port `openclaw.net`, or third-party agent-persona repos. Docs were read on 2026-09-29. The architecture comparison page says its source review was refreshed 2026-08-27 against commit `7b624e9de25` and that those are development snapshots, so installed versions can differ.

## What is the current official product and repo, and what did it used to be called?

### Takeaway
OpenClaw is a MIT-licensed, self-hosted Gateway that connects chat apps to an always-on agent on the operator’s hardware. The official lore page says it began as Warelay, was Clawd/Clawdbot, molted to Moltbot on 2026-01-27 after an Anthropic trademark request, and became OpenClaw on 2026-01-30.

### Cited Findings
- OpenClaw is “your AI assistant, on your own hardware, in every chat app you already use,” with “one Gateway,” “any model,” “any device,” and “no hosted service in the middle.” It is developed by the OpenClaw Foundation, an independent 501(c)(3), with “no paid tier” and “no telemetry by default beyond a version check you can turn off.” — [OpenClaw docs home](https://docs.openclaw.ai/)
- It is a self-hosted gateway that connects Discord, Google Chat, iMessage, Matrix, Microsoft Teams, Signal, Slack, Telegram, WhatsApp, Zalo, “and more via channel plugins” to AI coding agents. One Gateway process on the operator’s machine or a server is the bridge. The same gateway is a personal assistant or a shared team deployment; “configuration is the only difference.” License framing on the home page is “open source”; the credits page states MIT, copyright OpenClaw Foundation. — [Docs home](https://docs.openclaw.ai/); [Credits](https://docs.openclaw.ai/reference/credits)
- Runtime requirement on the docs home: Node 26 recommended, or Node 24.16+ or Node 26.1+. An API key from the chosen provider is required. Install is `curl -fsSL https://openclaw.ai/install.sh | bash` (macOS/Linux/WSL2) or the PowerShell installer; other methods (npm, pnpm, bun, Docker, Nix, from source) are pointed at the Install page. Config lives at `~/.openclaw/openclaw.json`. Default local Control UI is `http://127.0.0.1:18789/`. — [Docs home](https://docs.openclaw.ai/)
- Creator credited as Peter Steinberger (`@steipete`). — [Credits](https://docs.openclaw.ai/reference/credits)
- Name history on the official lore page: origin name **Warelay**, “a sensible name for a WhatsApp gateway”; then **Clawd** living in a **Clawdbot**; on an unspecified morning in January 2026 Anthropic “sent a polite email asking for a name change (trademark stuff)”; **Moltbot** “won” at a 2026-01-27 Discord naming session; “On January 30, 2026” it became **OpenClaw**. The same page says the 2026-01-30 migration renamed GitHub to `github.com/openclaw/openclaw`, secured the X handle `@openclaw`, released npm packages under the new name, and moved docs to `docs.openclaw.ai`. Clawd is dated “Nov 25, 2025 – Jan 27, 2026.” — [OpenClaw lore](https://docs.openclaw.ai/start/lore)
- The architecture page says the Foundation “sells nothing: no paid tier, no hosted service, no token.” The only default request an install makes to the Foundation is a version check; `update.checkOnStart: false` turns it off. Model-provider and channel traffic goes to those services, not the Foundation. Releases are signed under the Foundation identity. The whole product is MIT with “no enterprise edition.” Donors/partners named there include Amazon, Atlassian, GitHub, Microsoft, NVIDIA, OpenAI, Red Hat, and Tencent. — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Why OpenClaw cites the repo tree `https://github.com/openclaw/openclaw/tree/7b624e9de25bc66c97166071c8d05f055d82ec54` as the 2026-08-27 review snapshot, and publishes security advisories at `https://github.com/openclaw/openclaw/security/advisories` (647 advisories listed on that snapshot date; the page says advisory counts are not a safety score). — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Legacy skill frontmatter key `metadata.clawdbot` is still accepted when `metadata.openclaw` is absent. — [Skills](https://docs.openclaw.ai/tools/skills)

### Inferences
- Clawdbot, Moltbot, and OpenClaw are successive names of one project, not three products. Warelay is the pre-lobster gateway name in the project’s own lore, not a separate current product.
- “No hosted service” means the Foundation does not sell a cloud OpenClaw. It does not mean the agent never calls cloud model APIs or optional cloud workers (those are covered below).

### Gaps
- The lore page is narrative. It does not give a formal changelog of binary/package renames, config-path migrations, or the intermediate name “CLAWDIS,” which appears in secondary writeups but not on the official pages opened here.
- Exact current release tag and star count were not taken from the GitHub Releases or README pages; those pages were not opened. The docs home does not print a version number.

## Which channels does it attach to (chat apps, email, voice, local UI)?

### Takeaway
One Gateway serves many chat channels at once. Telegram and WebChat ship closer to core; most other messengers are official plugins. Local interfaces are the browser Control UI, WebChat, a macOS menu-bar app, and paired iOS/Android/watchOS nodes. Email and phone calls exist as separate automation/plugin surfaces named from indexes, not as another chat channel in the catalog.

### Cited Findings
- The Gateway is the single source of truth for sessions, routing, and channel connections. Diagram: chat apps and plugins, CLI, Web Control UI, macOS app, and iOS/Android nodes all attach to the Gateway, which also hosts the OpenClaw agent. — [Docs home](https://docs.openclaw.ai/)
- Official channel catalog (generated in the docs): A2A (bundled; external agents via A2A 1.0 JSON-RPC), Buzz, ClickClack, Discord (docs blurb includes “voice”), Feishu, Google Chat, iMessage (via `imsg`, JSON-RPC over stdio, “private API actions” for replies, tapbacks, effects, polls, attachments, group management), IRC, LINE, Matrix, Mattermost, Microsoft Teams, Nextcloud Talk, Nostr (NIP-04 DMs), QQ bot, Raft, Reef (bundled; “guarded, end-to-end-encrypted messaging between OpenClaw agents of different people”), Signal (via signal-cli), Slack, SMS (Twilio SMS/MMS, official plugin), Synology Chat, Telegram (bundled), Tlon, Twitch, WebChat (included in core, Gateway WebSocket), WeChat (external plugin), WeCom (external), WhatsApp (official plugin), Yuanbao (external), Zalo, Zalo ClawBot (external), Zalo personal (official plugin, QR login). Related: Voice Call plugin, “telephony via Plivo, Telnyx, or Twilio.” — [Chat channels](https://docs.openclaw.ai/channels)
- Features page restates: A2A, Reef, Telegram, and WebChat ship with the core install; every other channel is an official plugin (`openclaw plugins install @openclaw/<id>` or on demand during onboard / `channels add`). External plugins maintained outside the repo: WeChat, Yuanbao, Zalo ClawBot. Group chats use mention-based activation. DMs use allowlists and pairing. — [Features](https://docs.openclaw.ai/concepts/features)
- Recommended first channel is Telegram (bot token, no plugin install). WhatsApp needs QR pairing and stores more state. Channels can run simultaneously and route per chat. — [Chat channels](https://docs.openclaw.ai/channels)
- Default if unconfigured: bundled OpenClaw agent runtime; DMs share the agent’s main session; each group chat gets its own session. Example lock-down is `channels.whatsapp.allowFrom` plus group `requireMention`. — [Docs home](https://docs.openclaw.ai/)
- Local and companion UIs: WebChat and browser Control UI; macOS menu bar companion; iOS node (pairing, camera, screen recording, location, voice); Android node (pairing, chat, voice, camera, device commands); “Windows Hub” is named under Apps and UI. Media in/out includes images, audio, video, documents, plus voice-note transcription and text-to-speech. — [Features](https://docs.openclaw.ai/concepts/features); [Docs home](https://docs.openclaw.ai/)
- A node is a companion (macOS, iOS, watchOS, Android, or headless) that connects with `role: "node"` and exposes commands such as `camera.*`, `device.*`, `notifications.*`, `system.*` via `node.invoke`. Most nodes use the Gateway WebSocket on the operator port. An optional direct Apple Watch node uses signed HTTPS polling because watchOS blocks generic low-level networking. Nodes are peripherals: they do not run the gateway, and channel messages land on the gateway, not on nodes. macOS menu-bar app can run in node mode and add widget-panel, camera, screen, notification, and computer-control commands. — [Nodes](https://docs.openclaw.ai/nodes)
- Node index lists Talk mode as “live voice conversation on a node” and Voice wake as “wake-word capture on a node,” plus camera, screen recording, location, SMS on Android nodes, and device/personal-data commands. — [Nodes](https://docs.openclaw.ai/nodes)
- Group-join introductions (Discord, LINE, Matrix, Slack, Telegram) run with no tools, treat room history as untrusted, and are bounded to 60 seconds. Ambient room events are mentioned as a way unmentioned chatter becomes quiet context unless the agent sends with the `message` tool. Bot-loop protection exists for channels that accept bot-authored inbound messages. — [Chat channels](https://docs.openclaw.ai/channels)
- Security defaults: on a regular host install the Gateway binds to loopback; most channels answer an unknown DM with a pairing code instead of processing it; group access is allowlisted, usually behind a mention gate. Container images default to an exposed bind. A few workspace channels such as ClickClack trust workspace membership by default. — [Security](https://docs.openclaw.ai/gateway/security)

### Inferences
- The product’s primary UX is “message the assistant from apps you already use,” plus a local dashboard, not a single terminal REPL. The CLI exists (`openclaw onboard`, `openclaw gateway install`, `openclaw dashboard`) as control plane, not as the only session.
- Voice is split: channel voice notes / TTS, a Talk/voice-wake node surface, Discord’s own voice (named only in the Discord catalog blurb), and a separate telephony plugin. Those are not one speech stack.

### Gaps
- Per-channel media, reaction, and voice capability matrices were not opened (only the catalog blurbs and the features summary). Discord “voice,” Talk mode internals, Voice Call setup, and SMS webhook details live on child pages that were not fetched.
- No opened page lists email or calendar as a chat channel. Gmail/IMAP automation appeared only in search snippets of docs pages that were not opened, so it is not treated as a confirmed channel here.
- Whether WebChat is the same surface as the Control UI, or a panel inside it, is not fully specified on the pages opened (both are named).

## What tools and capabilities does the runtime give the model?

### Takeaway
The model gets a policy-filtered tool list: shell and processes, workspace files, web search/fetch, an isolated browser tool, messaging, sessions and sub-agents, cron/heartbeat, Gateway and paired-node device commands, media generation, and a `computer` tool for desktop control. Email, calendar, smart home, and payments are not first-party tools on the pages opened; the extension path is skills, plugins, and MCP.

### Cited Findings
- Tools are typed functions sent to the model as schemas. Skills are `SKILL.md` instruction packs. Plugins add tools, skills, channels, providers, speech, realtime voice, media generation, web search, web fetch, hooks, and other runtime capabilities. The model only sees tools that survive the active profile, allow/deny policy, provider restrictions, sandbox state, channel permissions, and plugin availability. — [Tools overview](https://docs.openclaw.ai/tools)
- Built-in categories and representative tools from that overview: Runtime `exec`, `process`, `terminal`, `code_execution`; Files `read`, `write`, `edit`, `apply_patch`; Human input `ask_user`, `secrets`; Web `web_search`, `x_search`, `web_fetch`; Browser `browser`; Operator UI `screen`, `theme`; Session progress `progress_card` (unavailable to sub-agents); Messaging `message`; Sessions and agents `sessions_*`, `agents_wait`, `subagents`, `agents_list`, `session_status`, `get_goal`, `create_goal`, `update_goal`; Automation `cron`, `heartbeat_respond`; Gateway and nodes `gateway`, `nodes`; Plugin lifecycle `plugins`; Media `view_image`, `image_generate`, `music_generate`, `video_generate`, `tts`. Large catalogs can use `exec`, `wait`, `tool_search`, `tool_describe`, `tool_call` instead of sending every schema. Code Mode and Tool Search are called experimental OpenClaw agent surfaces; Codex harness runs use Codex-native code mode and tool search instead of `tools.codeMode` / `tools.toolSearch`. — [Tools overview](https://docs.openclaw.ai/tools)
- Plugin-provided tools named there: diffs, show widget (inline SVG/HTML), screen, LLM Task (JSON-only workflow steps), Lobster (“typed workflows with resumable approvals”), Tokenjuice (compacting noisy exec/bash output), Tool Search, Canvas (macOS widget panel and A2UI). — [Tools overview](https://docs.openclaw.ai/tools)
- Web search providers listed on the features page: Brave, DuckDuckGo, Exa, Firecrawl, Gemini, Grok, Kimi, MiniMax Search, Ollama Web Search, Perplexity, SearXNG, Tavily. Also listed: browser automation, exec, sandboxing, cron jobs and heartbeat scheduling, skills, plugins, and “workflow pipelines (Lobster).” Shared image and video generation surfaces. — [Features](https://docs.openclaw.ai/concepts/features)
- Browser is one agent tool named `browser` in the tools table (“operate a browser session”). Computer use is a separate built-in `computer` tool that sees and controls the Gateway desktop or a paired node’s desktop through `computer.act` and `screen.snapshot`. A vision-capable model drives it. Actions include screenshot, clicks, drag, scroll, type, key combos, and wait; capable providers add windows, accessibility trees, app launch/kill, and a CUA browser family. Screenshots are model-only and are not auto-delivered to the chat channel. On-screen content is untrusted. macOS default provider is Peekaboo; CUA is an app-owned driver. Windows/Linux `cua-computer` is optional and experimental and currently controls only the primary display, with several input actions unavailable. Local onboarding selects a Full tool profile when none is configured, but an explicit `coding` profile excludes `computer` unless added to `tools.alsoAllow`. — [Computer use](https://docs.openclaw.ai/nodes/computer-use); [Tools overview](https://docs.openclaw.ai/tools)
- Nodes expose camera, screen recording, location, Android SMS, notifications, system commands, file transfer, and node-hosted MCP servers, skills, and local model inference. Exec can be pointed at a node; commands are allowlisted. Session catalogs can discover Codex, Claude, OpenCode, and Pi sessions on the Gateway and paired nodes. — [Nodes](https://docs.openclaw.ai/nodes)
- Coding harnesses can be the execution runtime while OpenClaw keeps channels, sessions, policy, and state: Codex plugin drives Codex’s app-server loop (native thread resume, compaction, approvals, mid-turn steering, OpenClaw tools bridged in, computer use); a Copilot plugin runs the GitHub Copilot SDK session loop; the Anthropic plugin drives the installed Claude Code executable over structured stdio. Fallback to OpenClaw’s built-in loop can be declared. The bundled `coding-agent` skill is opt-in (`skills.entries.coding-agent.enabled: true`) and needs `claude`, `codex`, `opencode`, or another supported CLI installed and authenticated. — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw); [Skills](https://docs.openclaw.ai/tools/skills)
- OpenClaw is an MCP client (Streamable HTTP, SSE, and stdio, with OAuth) and an MCP server. External agents can use A2A 1.0. Editors can use the Agent Client Protocol, which OpenClaw also uses to host external harnesses. The Gateway can serve an OpenAI-compatible API (`/v1/chat/completions` with a documented function-tool subset, `/v1/responses`, `/v1/models`, `/v1/embeddings`), disabled by default, with `/v1/responses` separately enabled. — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Where work runs: default is the operator’s Gateway host (loopback bind on a regular install). Execution can be moved, when configured, into a sandbox, a paired node, or a “throwaway cloud machine” without standing Gateway credentials. Sandboxing is off by default. Cloud workers and Cloud Worker Desktop are experimental Labs flags (`cloudWorkers.desktop`, Host Desktop `desktop.host.enabled`). Computer-use docs describe Crabbox / cloud-session desktops: the `computer` tool binds to that session’s desktop; a conversation can attach a temporary Crabbox while the agent stays on the Gateway; taking control in the Desktop panel pauses agent input. NVIDIA NemoClaw is described as a third-party distribution that hardens OpenClaw with OpenShell kernel sandboxing, not as the default runtime. — [Security](https://docs.openclaw.ai/gateway/security); [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw); [Experimental features](https://docs.openclaw.ai/concepts/experimental-features); [Computer use](https://docs.openclaw.ai/nodes/computer-use)
- Model calls leave the machine unless the operator picks a self-hosted provider. Features lists custom/self-hosted support: vLLM, SGLang, Ollama, llama.cpp, LM Studio, and any OpenAI-compatible or Anthropic-compatible endpoint, plus “many model providers (Anthropic, OpenAI, Google, and more)” and subscription auth via OAuth (example: OpenAI Codex). Memory search “uses OpenAI embeddings by default” unless `memory.search.provider` is set to Gemini, Voyage, Mistral, Bedrock, DeepInfra, local GGUF, Ollama, LM Studio, GitHub Copilot, or a generic OpenAI-compatible endpoint. — [Features](https://docs.openclaw.ai/concepts/features); [Memory overview](https://docs.openclaw.ai/concepts/memory)
- State the docs say stays local: workspace Markdown memory under the agent workspace (default `~/.openclaw/workspace`); config at `~/.openclaw/openclaw.json`; skill library records in `state/openclaw.sqlite` and revision bundles under the state directory. The home page says there is no hosted service in the middle. Protected credentials “can stay out of model context” via handles and egress substitution, with separate exposure risks for agent-readable entries, host access, and permitted-service responses. — [Docs home](https://docs.openclaw.ai/); [Memory overview](https://docs.openclaw.ai/concepts/memory); [Skills](https://docs.openclaw.ai/tools/skills); [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)

### Inferences
- “Personal agent” here is a local control plane plus a swappable model and a swappable executor. The user’s machine holds the Gateway, transcripts, memory files, and credentials; the model weights usually do not.
- Shell, browser, and computer use are first-class. Domain tools such as mail, calendar, smart home, and payments are not in the built-in tool table, so they would have to arrive as skills, plugins, MCP servers, or shell commands. That is an absence from the opened capability indexes, not proof that no plugin exists.

### Gaps
- The tools overview says its table is representative, not the full policy reference (`/gateway/config-tools` was not opened). Exact default allow/deny sets per profile were not copied.
- Browser isolation (dedicated Chrome profile, loopback control service, SSRF policy) is documented on `/tools/browser` and `/gateway/security/browser-control`, which were not fetched. Only the existence of a `browser` tool and a security section titled “Browser control risks” is confirmed from opened pages.
- Cron schedule kinds, heartbeat interval, Gmail Pub/Sub, and IMAP watcher behavior were visible in search snippets of `/automation/cron-jobs` and `/automation/gmail-pubsub` but those pages were not opened. Confirmed from opened pages: tools `cron` and `heartbeat_respond`, and the features line “cron jobs and heartbeat scheduling.”
- No opened page documents a built-in payments tool, a built-in calendar API, or a built-in smart-home bus. Lore’s future wishlist (as of the “2026.9 releases”) lists “a smart home to control (KNX + openhue)” and “ears (Brabble voice daemon in development)” as things Molty “may have,” which reads as not shipped core, but the lore page is not a capability spec. ClawHub search examples use the query “calendar”; that shows the registry can be searched for calendar skills, not that a calendar skill ships in core.
- Cloud worker provisioning, pricing, and who operates Crabbox were not opened. The Foundation page says the Foundation sells no hosted service; it does not say third-party worker hosts are free or absent.

## How do memory, identity, skills/plugins, and permissions work?

### Takeaway
Memory is Markdown in the agent workspace plus a SQLite-backed search index, not a hidden vector store the model secretly updates. Identity files named in lore (`SOUL.md`, `AGENTS.md`) are separate from the memory overview’s operational files (`USER.md`, `MEMORY.md`, daily notes). Skills are instructions; plugins are code. Permissions are config, pairing, tool policy, and optional sandboxing, and the project says sandboxing and exec approvals are off by default.

### Cited Findings
- “The model only remembers what gets saved to disk; there is no hidden state.” Files: optional `USER.md` (preferences and profile, loaded at session start with a small budget); `MEMORY.md` (curated long-term facts, loaded at session start); `memory/YYYY-MM-DD.md` daily notes (indexed, not injected every turn; today and yesterday load on a bare `/new` or `/reset`); optional `DREAMS.md` for dreaming-sweep summaries. Default workspace is `~/.openclaw/workspace`. If `MEMORY.md` exceeds the bootstrap budget, the file on disk stays intact and the injected copy is truncated. — [Memory overview](https://docs.openclaw.ai/concepts/memory)
- Tools: `memory_search` (hybrid semantic plus keyword when an embedding provider is configured), `memory_get` (a memory file or line range), `intent` (event-conditioned standing intents). Time-based reminders use scheduled tasks. All three come from the active memory plugin; default is `memory-core` (SQLite, keyword, vector, hybrid, “no extra dependencies”). Other engines named: Honcho (plugin) and LanceDB (plugin). Optional `memory-wiki` compiles a vault beside the active plugin and does not replace it. — [Memory overview](https://docs.openclaw.ai/concepts/memory)
- Before compaction, a silent memory-flush turn runs by default so the agent can write important context to memory files (`agents.defaults.compaction.memoryFlush.enabled: false` turns it off). Dreaming is the default background consolidation path into `MEMORY.md`, on unless `plugins.entries.memory-core.config.dreaming.enabled: false`. Promotions are score-gated; “untrusted and system-derived candidates never enter the consolidation prompt or durable promotion path.” “Memory can preserve approval context, but it does not enforce policy.” — [Memory overview](https://docs.openclaw.ai/concepts/memory)
- Control UI can import Markdown memory from Codex (`~/.codex/memories` consolidated files only), Claude Code project auto-memory, and Hermes `MEMORY.md` / `USER.md`. Imports stay under `memory/imports/...`, are searchable, and are not merged into bootstrap `MEMORY.md`. — [Memory overview](https://docs.openclaw.ai/concepts/memory)
- Provenance limits stated on the architecture page: attributable memories can be purged and forgotten-session records prevent reingestion through participating paths; original transcripts, untracked writes, and external copies remain. “Promoted memories have no time-based retention bound.” Admission exclusions apply to dreaming ingestion and session backfill, not direct writes, hooks, or raw transcript indexing. Turn taint covers network-sourced tool output; text from non-network tools does not taint the turn. CLI named: `openclaw memory forget`. — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Lore calls these “sacred texts”: `SOUL.md` (“Molty’s identity document”), `memory/*.md`, `AGENTS.md` (operating instructions), `USER.md` (context about the creator). Molty “lives in `~/.openclaw/workspace/`.” That list is not repeated on the memory overview, which does not mention `SOUL.md` or `AGENTS.md`. — [Lore](https://docs.openclaw.ai/start/lore); [Memory overview](https://docs.openclaw.ai/concepts/memory)
- On multi-user Gateways, `personal_instructions` reads and updates the authenticated requester’s personal `USER.md` through the Gateway and does not widen general file-tool access. It is included in the coding and messaging profiles. — [Tools overview](https://docs.openclaw.ai/tools)
- Skills are AgentSkills-format `SKILL.md` files (YAML frontmatter plus body). Precedence, highest first: workspace `skills`, project `.agents/skills`, personal `~/.agents/skills`, managed `<state-dir>/skills`, workshop skills, bundled and Custodian skills, then extra dirs and plugin skills. Same name: highest source wins. Discovery finds `SKILL.md` up to 6 levels deep and does not walk up to a parent repo. Allowlists (`agents.defaults.skills` / per-agent `skills`) control visibility separately from location; an empty per-agent list exposes no skills; omitting the default list leaves skills unrestricted by that control. Allowlists are “not a host shell authorization boundary.” — [Skills](https://docs.openclaw.ai/tools/skills)
- Skills load on demand in the sense that explicit `$skill` references (up to eight per message) tell the model to read each `SKILL.md` before acting. `disable-model-invocation: true` keeps a skill out of the model’s normal prompt; an authorized explicit reference can still invoke it. `command-dispatch: tool` can bypass the model and call a tool directly. Gating uses `metadata.openclaw.requires` (bins, env, config) and an `os` filter. Third-party skills are “untrusted code”; `security.installPolicy` can run a local command before installs and fails closed. `skills.entries.*.env` and `apiKey` inject into the host process for that turn, not into the sandbox. ClawHub (`clawhub.ai`) is the public registry; `openclaw skills verify` checks a trust envelope. VirusTotal, ClawScan, and static analysis are named. “A pending or stale scan can allow installation with a warning.” `skills-sh:` installs are “Not scanned by ClawHub.” — [Skills](https://docs.openclaw.ai/tools/skills); [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Plugins: channels, providers, memory, voice, and the Codex harness ship as plugins. The public plugin SDK has “about 150 entrypoints.” Native plugins “run in-process and are not sandboxed.” Operator mitigations named: allow-lists, an install-policy hook, pinned versions, dependency locking, CI-enforced SDK boundaries. `plugins.allow` can pin the allowed set. All plugin APIs are experimental; that label does not require a Labs switch except for custom Control UI views. — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw); [Experimental features](https://docs.openclaw.ai/concepts/experimental-features)
- Multi-agent: “isolated sessions per agent, workspace, or sender.” Direct chats collapse into shared `main`; groups are isolated by default. Sub-agents, swarm, and agent-send are separate capability pages linked from the tools overview. Session tools accept `user` (verified `requester_profile.id`) when several people steered the turn. A shared gateway records an immutable session creator, an assignable owner, and who prompted; Control UI shows who is viewing and typing; drafts stay ephemeral and never reach the model or the transcript. — [Features](https://docs.openclaw.ai/concepts/features); [Docs home](https://docs.openclaw.ai/); [Tools overview](https://docs.openclaw.ai/tools); [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Permission model from the security index and the architecture page: one trust boundary per gateway (a single operator, or a team whose members trust each other). “OpenClaw is not a hostile multi-tenant security boundary.” DM policies include pairing, allowlist, open, and disabled. Tool policy is enforced before the model call; if a tool is removed, its schema is not sent. Exec approvals and elevated exec exist as separate docs. Sandboxing and exec approvals are off by default: “Default OpenClaw is a trusted single-operator assistant.” Hardening is configuration; `openclaw security audit` reports drift. Full access with no sandbox is a documented posture, as are read-only mode and per-agent access profiles. Agents with the message tool can send across conversations and channel providers by default unless cross-provider messaging is restricted. Node execution (`system.run`) is a distinct control. Sub-agent delegation has a guardrail section. Secrets land on disk; transcripts and logs are called out as a storage concern. — [Security](https://docs.openclaw.ai/gateway/security); [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Computer-use authorization is above the driver: tool exposure, dangerous-command allowlist, device and command pairing approval, node-local provider enablement, and OS permissions (macOS Accessibility, Screen Recording, and for Peekaboo Event Posting). The macOS CUA daemon is started “unrestricted” with approvals bypassed because bounded manifests cannot express discovered windows; the Gateway is described as the chokepoint. Same-user processes are inside that boundary and “may be able to discover and use same-user resources.” Unrestricted CUA “does not contain a compromised user account.” High-risk families (forced app kill, browser navigation, downloads, file inputs, recording, trajectory replay, desktop-scope escalation) are classified before dispatch but “classification does not add a per-action prompt.” — [Computer use](https://docs.openclaw.ai/nodes/computer-use)
- `ask_user` pauses for a structured decision owned by the user. `secrets` is described as obtaining a credential without the model seeing it. — [Tools overview](https://docs.openclaw.ai/tools)

### Inferences
- Identity is file-shaped and editable by the operator and the agent, not an account at the Foundation. Operational memory and the lore “soul” document are easy to conflate; only `USER.md` / `MEMORY.md` / daily notes are specified as the memory system.
- A skill does not grant a tool. Installing a calendar or Home Assistant skill would still depend on whatever binaries, env vars, and tools that skill’s text tells the model to use, plus tool policy.
- Default personal use is powerful and weakly confined: the process user can run tools the policy still exposes, and sandboxing is an opt-in.

### Gaps
- The full tool-profile matrix (what `coding` vs `messaging` vs `minimal` vs `full` includes) was not opened. The tools page says `personal_instructions` is in coding and messaging profiles; the computer-use page says an explicit coding profile excludes `computer`.
- `SOUL.md` and `AGENTS.md` contents, whether they are injected every turn, and their size caps are not specified on the memory overview. No bootstrap-prompt template was opened.
- Honcho and LanceDB behavior beyond the one-line cards was not opened.
- Exact exec approval UX (when a human is prompted, session-wide allow, deny-rule syntax) is on `/tools/exec-approvals`, not fetched.
- ClawHub malware history and current scan pass rates were not opened. The architecture page’s warning about pending scans is the confirmed limitation.

## What is explicitly experimental, unsafe, or called out as a limitation?

### Takeaway
The project’s own “what we do not claim” list is the limitation statement: sandbox and exec approvals off by default, one gateway is one trust domain, native plugins are in-process, egress allowlists do not bind raw unsandboxed sockets, and memory deletion does not cover every copy. Several desktop and orchestration surfaces are Labs/experimental.

### Cited Findings
- Experimental means off by default unless the feature docs say otherwise, and shape can change faster than stable config. Documented flags: Codex harness `plugins.entries.codex.config.appServer.experimental.sandboxExecServer` (native Codex app-server 0.143.0+ can target an OpenClaw sandbox-backed exec server); Code Mode `tools.codeMode.enabled` (off until Labs or explicit `true` / `"auto"`); Cloud workers desktop `cloudWorkers.desktop`; custom plugin UI `gateway.controlUi.experimental.customPlugins` (off by default); Host Desktop `desktop.host.enabled` (watch or control the Gateway host through its VNC or Screen Sharing server); Tool Search `tools.toolSearch.enabled` (enabled when unset). Labs also lists Decision assistance, which “saves intent but connects no automatic Decision consumers” and “does not start inference.” All plugin APIs are experimental. Local model lean mode is an advanced troubleshooting override outside Labs. — [Experimental features](https://docs.openclaw.ai/concepts/experimental-features)
- “What we do not claim”: sandboxing and exec approvals off by default; one gateway is one trust domain and “fleet is still experimental”; native plugins run in-process and are not sandboxed; egress allowlisting covers cooperating traffic only, while “raw sockets from unsandboxed host exec answer to an operator-supplied proxy or host policy, not to OpenClaw”; sandboxed execution defaults to kernel-enforced `network: "none"` or OpenShell default-deny, but that is the configured sandbox, not the default install; promoted memories have no time-based retention bound; `gateway.roles` existed in the August 2026 snapshot and should be checked on the installed version. — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Prompt injection is a documented threat page (untrusted content, wrapping, bypass flags that should stay off, reasoning/verbose output in groups). Group-join introductions specifically run with zero tools because room text is third-party content. Computer-use screenshots are untrusted input. — [Security](https://docs.openclaw.ai/gateway/security); [Chat channels](https://docs.openclaw.ai/channels); [Computer use](https://docs.openclaw.ai/nodes/computer-use)
- Container images default to an exposed bind and must be paired with auth. mDNS/Bonjour discovery, Tailscale, reverse proxies, and “insecure/dangerous flags” are separate hardening topics. `openclaw security audit` is the drift check. — [Security](https://docs.openclaw.ai/gateway/security)
- Windows and Linux computer use via `cua-computer` is “experimental.” It controls only the primary display; held mouse buttons, modifier-held clicks, scrolling, and dragging are rejected on that fulfiller; a same-geometry display swap inside one session cannot be detected. macOS CUA unrestricted mode does not contain a compromised same-user account. Gateway computer control requires explicit plugin enablement and does not silently fall back to a paired node. — [Computer use](https://docs.openclaw.ai/nodes/computer-use)
- Skill security: treat third-party skills as untrusted code; symlink/realpath containment has explicit exceptions; upload-archive skill install is off unless `skills.install.allowUploadedArchives: true`. ClawHub verification is not a hash of current local files in the architecture page’s description of `openclaw skills verify`, and a pending or stale scan can still install with a warning. — [Skills](https://docs.openclaw.ai/tools/skills); [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Memory flush is skipped when the sandbox workspace is read-only or inaccessible. Dreaming will not promote untrusted or system-derived candidates, but direct writes are outside that gate. — [Memory overview](https://docs.openclaw.ai/concepts/memory); [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- iOS realtime Talk and Android realtime Talk were described on an unopened provider page in search results as pending device proof. The opened nodes index only says Talk mode and voice wake exist. Do not treat mobile realtime as shipped from these notes. — [Nodes](https://docs.openclaw.ai/nodes) (index only)

### Inferences
- The unsafe default is intentional for a single trusted operator: the agent can act as the user until someone turns sandboxing, exec approvals, and tool profiles on. That is the opposite of a default-deny coding sandbox.
- Experimental cloud/desktop control is real product surface, but it is not the default personal install.

### Gaps
- No opened page lists a current CVE or says which historical issues remain unfixed. The advisory count (647 as of 2026-08-27) is a disclosure-record statistic the project itself says not to read as a safety score. Individual advisories were not opened.
- Decision assistance, Code Mode, and Tool Search quality or failure modes were not tested; only their flags and “foundation only” wording for Decision assistance.
- Host Desktop VNC threat model was not opened beyond the flag description and the cloud-worker desktop paragraph on Why OpenClaw (loopback-only RFB, single-use ticket, view-only filtering for Cloud Worker Desktop).

## How is this different in shape from a coding-agent CLI (one repo, one terminal session)?

### Takeaway
OpenClaw is an always-on, multi-channel Gateway that owns sessions, credentials, routing, and policy, and can embed a coding CLI’s harness as a plugin. A coding CLI is one person, one terminal, one workspace; OpenClaw is built to keep running when that terminal is closed and to be reached from phones and chat apps, including by more than one person on one trust boundary.

### Cited Findings
- The home page’s job statement is a Gateway between chat apps and an agent, not a repo-scoped coding session. If you do nothing, DMs share one main session and each group gets its own. The Gateway stays up as a background service after `openclaw gateway install`. — [Docs home](https://docs.openclaw.ai/)
- “Most agent-assisted work today happens between one person and one terminal; others see the finished commits.” A shared OpenClaw gateway is described as making the work observable: sessions have a creator, an owner, and the people who prompted; a channel conversation can continue as a session the team can open, steer, and take over; local coding sessions can be mirrored to a team gateway with Beam; cloud workers put execution on disposable machines while the transcript stays shared. There is no separate enterprise edition. — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- The vendor harness (Codex app-server, Claude Code executable, Copilot SDK) is a plugin runtime. OpenClaw “keeps ownership of channels, sessions, policy, and state.” Gateways that only call a vendor API “keep their own executor in charge.” — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- Proactive surface that a one-shot CLI session does not have: cron and heartbeat tools, dreaming’s recurring consolidation job, and channel delivery of agent-originated messages. Automation is a top-level docs area (“run work on a schedule with cron jobs, hooks, and webhooks”). — [Docs home](https://docs.openclaw.ai/); [Tools overview](https://docs.openclaw.ai/tools); [Features](https://docs.openclaw.ai/concepts/features)
- Device shape a terminal session does not have: paired phone/watch/Mac nodes with camera, screen, location, talk, and computer use, while channel ingress still terminates at the Gateway. — [Nodes](https://docs.openclaw.ai/nodes); [Docs home](https://docs.openclaw.ai/)
- Contrast the project itself draws with a single-process harness: a single trust envelope puts the agent loop, channel connections, credentials, and shell under one OS user; a VM around that whole app isolates it from the host but not those pieces from each other. OpenClaw’s intended split is a trusted Gateway and movable untrusted execution. That split is configuration, not the default (sandbox off). — [Why OpenClaw](https://docs.openclaw.ai/start/why-openclaw)
- It is still a coding agent when used that way: features call it “built for coding agents with tool use, sessions, memory, and multi-agent routing,” file tools and `exec` are built in, and node session catalogs surface Codex, Claude, OpenCode, and Pi sessions. The coding profile is one tool profile among others, not the whole product. — [Docs home](https://docs.openclaw.ai/); [Nodes](https://docs.openclaw.ai/nodes); [Computer use](https://docs.openclaw.ai/nodes/computer-use)

### Inferences
- The harness boundary is the Gateway process and its policy, not the model’s tool loop. Swapping Claude Code or Codex changes who runs the turn; it does not replace channel routing or the on-disk session store.
- Multi-user is collaboration inside one trust domain (shared secrets, shared host), not tenant isolation. That is a product-shape difference from both a personal CLI and a multi-tenant SaaS agent.

### Gaps
- Session file formats (`sessions.json`, transcripts, retention) were not opened; only the behavioral claims above.
- Beam, Portals, and team setup steps were not opened beyond the architecture summary.
- No opened page quantifies idle cost, heartbeat frequency, or whether the Gateway must stay running for cron to fire. The existence of a background Gateway service and cron/heartbeat tools is what is confirmed.
