# Embeddable agent SDK harness primitives (as of 2026-09-29)

Scope is runtime machinery around the model (tools, approvals, sessions, sandboxes, hooks, MCP, memory, compaction), not prompt wording. Claims below are from pages opened or from official-doc extracts returned by search on 2026-09-29. SDK-shipped behavior is labeled as a primitive; caller-supplied functions, editors, and sandbox implementations are application code the SDK invokes.

Products covered: Claude Agent SDK (Python and TypeScript; formerly Claude Code SDK), OpenAI Agents SDK (Python docs; JS tracing noted), OpenAI Responses API hosted tools, OpenAI Agents API (managed Codex harness), Codex SDK (`@openai/codex-sdk`, separate from the Agents SDK), Google ADK, Gemini CLI extensions, Microsoft Agent Framework, Pydantic AI, LangGraph, Hugging Face smolagents, Mastra, Vercel AI SDK `ToolLoopAgent`.

## Tool execution model: streaming, parallel calls, structured outputs, human-in-the-loop approvals

### Takeaway
Serious SDKs own the tool loop (model proposes calls, the runtime executes or pauses, results re-enter the model) and treat approval as a first-class pause/resume, not a prompt. Parallelism is usually conditional on read-only vs mutating tools. Structured outputs exist as a stop condition, not as a substitute for the tool loop.

### Cited Findings
- Claude Agent SDK embeds Claude Code's loop: the SDK receives the prompt plus system prompt, tool definitions, and history; Claude may emit text and/or tool calls; the SDK executes tools and feeds results back until a response has no tool calls. The app sees a stream of `SystemMessage`, `AssistantMessage`, `UserMessage` (tool results), optional `StreamEvent` (partials), and a terminal `ResultMessage`. Turns do not yield control back to application code between tool rounds unless the caller uses streaming input. `max_turns` / `maxTurns` counts tool-use turns only; `max_budget_usd` / `maxBudgetUsd` stops on spend. Result subtypes include `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, and `error_max_structured_output_retries`. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Claude built-in tools shipped with the SDK (not app code): file `Read`/`Edit`/`Write`, search `Glob`/`Grep`, `Bash`, web `WebSearch`/`WebFetch`, `ToolSearch`, orchestration `Agent`/`Skill`/`AskUserQuestion`/`TaskCreate`/`TaskUpdate`. When one turn requests several tools, read-only tools (`Read`, `Glob`, `Grep`, MCP tools marked read-only) may run concurrently; mutating tools (`Edit`, `Write`, `Bash`) run sequentially. Custom tools default to sequential; `readOnlyHint` opts them into parallel execution. Denials are returned to the model as tool results, not as a crashed turn. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Claude permission modes are SDK options: `default` (prompt via `canUseTool`, else deny), `acceptEdits` (auto-approve file edits and common filesystem commands), `plan` (no auto-approved edits), `dontAsk` (deny anything that would prompt), `auto` (model classifier), `bypassPermissions` (skip prompts except explicit ask rules and tools that require interaction; TypeScript also requires `allowDangerouslySkipPermissions`; refused as root on Unix outside a recognized sandbox). Allow rules can be command-scoped (`Bash(npm *)`). `allowedTools` auto-approves listed tools; unlisted tools remain available and fall through to the mode. `disallowedTools` blocks regardless of other settings. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Claude SDK overview lists the library primitives as built-in tools, hooks, subagents, MCP, permissions, sessions, skills/commands/memory, and plugins. The Client SDK's tool runner is a separate, thinner loop the application drives; Managed Agents is a hosted harness, not this library. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- OpenAI Agents SDK (Python) tool categories that the runner knows: hosted OpenAI tools (`WebSearchTool`, `FileSearchTool`, `CodeInterpreterTool`, `HostedMCPTool`, `ImageGenerationTool`, `ToolSearchTool`, `ProgrammaticToolCallingTool`); local runtime tools (`ComputerTool`, `ApplyPatchTool`, `ShellTool` local or hosted); `FunctionTool` from Python callables with schema generated from the signature; agents as tools (`Agent.as_tool`) without a handoff; experimental Codex tool. `@function_tool` docstring becomes the description; Pydantic/griffe build the input schema. Calling `__wrapped__` bypasses schema validation, guardrails, timeouts, and tracing. — [Tools](https://openai.github.io/openai-agents-python/tools/)
- OpenAI hosted tool search (`ToolSearchTool`) defers function tools marked `defer_loading=True`, namespaces, and hosted MCP until the model loads them. Exactly one `ToolSearchTool()` per agent. `ToolSearchTool(execution="client")` is not auto-executed by `Runner`; the runner raises. Programmatic tool calling runs model-generated JavaScript in a fresh hosted V8 isolate with no Node APIs, filesystem, or network; only tools opted in via `allowed_callers` are callable. Program-owned calls still go through the runner lifecycle (guardrails, hooks, timeouts, approvals, sessions, `RunState`). — [Tools](https://openai.github.io/openai-agents-python/tools/)
- OpenAI HITL is a runner primitive: `needs_approval=True` or a per-call async predicate on `function_tool`, `Agent.as_tool`, local `ShellTool`, and `ApplyPatchTool`. Local shell and apply-patch default `needs_approval=False`. If approval is required and no stored decision exists, the run pauses and `RunResult.interruptions` holds `ToolApprovalItem`s. The app serializes `RunState` (`to_json` / `to_string`), calls `approve` or `reject` (optional `always_approve` / `always_reject` sticky for the rest of the run, and optional per-call `rejection_message`), then `Runner.run` / `run_streamed` on the original top-level agent. Nested `Agent.as_tool` approvals surface on the outer run. Callable approval rules fail closed on missing, empty, non-object, or non-finite JSON arguments. Hosted MCP uses `require_approval` plus optional `on_approval_request`; hosted shell does not support SDK `needs_approval`. Local MCP servers (`MCPServerStdio`, `MCPServerSse`, `MCPServerStreamableHttp`) take `require_approval`. Streaming runs must drain `stream_events()` before inspecting interruptions. — [Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)
- OpenAI docs state the SDK's small primitive set as agents, handoffs / agents-as-tools, and guardrails, plus built-in tracing, function tools, MCP, sessions, and human-in-the-loop. Input guardrails run only on the first agent; output guardrails only on the agent that produces the final output; tool guardrails run on every guarded function-tool call, including local MCP tools when the server configures them. Hosted tools and built-in execution tools are called out as outside the function-tool guardrail pipeline in the guardrails page extract. A tripwire persists completed tool calls and required reasoning context and drops the rejected candidate final output, for both streaming and non-streaming runs. — [Overview index](https://openai.github.io/openai-agents-python/); [Guardrails](https://openai.github.io/openai-agents-python/guardrails/)
- Platform comparison (Responses vs Agents SDK vs Agents API) says the Agents SDK runner handles the loop and handoffs inside the application, while the Responses API is "calling models directly or building an agent from scratch" with hosted tools the app or the service runs, and the Agents API is a managed Codex harness. — [Agents](https://developers.openai.com/api/docs/guides/agents)
- Responses API shell is not on Chat Completions. `environment.type` of `container_auto` provisions a hosted container; `container_reference` reuses `container_id`. Docs tell callers to sandbox execution, apply allow/deny lists, and log activity. Hosted shell has no interactive TTY and no `sudo`. The model only proposes commands; the API forwards them to the container and streams output back into the next request. — [Shell guide (search extract)](https://developers.openai.com/api/docs/guides/tools-shell); [Tools (SDK binding)](https://openai.github.io/openai-agents-python/tools/)
- Computer use on the GA path is tool type `computer` with batched `actions[]` per `computer_call`; the older `computer-use-preview` model uses `computer_use_preview` plus environment and display size and one action per call. In the Agents SDK, `ComputerTool` is a local harness: the application implements `Computer` or `AsyncComputer` (screenshot, click, type, scroll, and so on). The SDK executes GA batched actions in order, then returns a screenshot `computer_call_output`. An application may instead expose its own browser/desktop operations as ordinary function tools; the model does not need the built-in computer tool. — [Tools](https://openai.github.io/openai-agents-python/tools/); [Computer use integration](https://developers.openai.com/api/docs/guides/tools-computer-use-integration)
- `ApplyPatchTool` always runs locally. The application implements `ApplyPatchEditor` (`create_file`, `update_file`, `delete_file`). SDK approval does not sandbox the editor. — [Tools](https://openai.github.io/openai-agents-python/tools/)
- Microsoft Agent Framework turns MCP `list_tools` results into `AIFunction` / agent tools and runs them via function calling. Python transports are `MCPStdioTool`, `MCPStreamableHTTPTool`, and `MCPWebsocketTool`. `allowed_tools` and `approval_mode` match raw remote names or unambiguous prefixed names; ambiguous normalized names raise `ToolExecutionException`. An agent can be exposed as an MCP server (`as_mcp_server()` in Python, `AsAIFunction` plus `McpServerTool` in .NET). Official tool-approval docs show per-function human approval: C# wraps `AIFunction` in `ApprovalRequiredAIFunction`; Python `@tool(..., approval_mode="always_require")`; Go `tool.ApprovalRequiredFunc`. — [Using MCP Tools](https://learn.microsoft.com/en-us/agent-framework/agents/tools/local-mcp-tools); [tool-approval.md](https://github.com/MicrosoftDocs/semantic-kernel-docs/blob/main/agent-framework/agents/tools/tool-approval.md)
- Pydantic AI ends a run with `DeferredToolRequests` (`approvals` and external `calls`) when a tool is marked `requires_approval=True`, raises `ApprovalRequired`, or is an external tool. Resume is a new `run` with prior message history plus `DeferredToolResults` (approve, `ToolDenied`, or `ToolApproved(override_args=...)`). `ApprovalRequiredToolset` can require approval dynamically for a whole toolset, including MCP. `args_validator` runs before deferral so invalid args never reach a human. `HandleDeferredToolCalls` is an optional capability that resolves those requests inside the same run instead of returning them. `output_type` can be a union of the normal type and `DeferredToolRequests`. — [Deferred tools](https://ai.pydantic.dev/deferred-tools/); [Handle deferred tool calls](https://pydantic.dev/docs/ai/capabilities/handle-deferred-tool-calls/)
- LangGraph `interrupt(value)` raises inside a node, persists graph state through a checkpointer, and waits indefinitely. Resume is `Command(resume=...)`. The node re-executes from the start; multiple interrupts in one node match resume values by order. Static `interrupt_before` / `interrupt_after` are documented as debugging breakpoints, not the recommended HITL path. LangChain's `humanInTheLoopMiddleware` (JS) and Deep Agents `interrupt_on` map tool names to allowed decisions `approve`, `edit`, `reject` (and `respond` in Deep Agents). A checkpointer is required; production docs name persistent savers such as Postgres or Mongo, not `MemorySaver`. — [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md); [JS human-in-the-loop](https://docs.langchain.com/oss/javascript/langchain/human-in-the-loop); [interrupt reference](https://reference.langchain.com/python/langgraph/types/interrupt)
- Vercel AI SDK `ToolLoopAgent` loops model calls and tool execution until a non-tool finish, a tool with no `execute`, an approval pause, or `stopWhen` (default `isStepCount(20)`). Current docs put policy on `toolApproval` (per-tool map or a function). Statuses include `not-applicable`, `approved`, and `user-approval`. Tool-level `needsApproval` is documented as deprecated but still honored; provider-executed tools ignore AI SDK approvals. Approval responses are fed back as tool-role messages and the agent is called again. Structured `output` schemas are a constructor option on the same class. — [ToolLoopAgent source comment](https://github.com/vercel/ai/blob/main/packages/ai/src/agent/tool-loop-agent.ts); [Tool approvals](https://sdk.vercel.ai/docs/agents/tool-approvals); [ToolLoopAgent reference](https://ai-sdk.dev/docs/reference/ai-sdk-core/tool-loop-agent)
- Mastra workflows pause with `suspend()` inside a step, persist a snapshot, and continue with `run.resume({ step, resumeData })` validated against `resumeSchema`. Agent networks emit suspend events for tools, sub-agents, and workflows and resume with `resumeNetwork`. This is framework workflow state, not a model-native tool protocol. — [Suspend and resume](https://mastra.ai/docs/workflows/suspend-and-resume); [Network approval](https://mastra.ai/docs/agents/network-approval)
- smolagents ships two loop styles as classes: `CodeAgent` (the model writes Python that calls tools; loops and conditionals are code, not extra model turns) and `ToolCallingAgent` (JSON/text tool calls). Sandboxed execution of that code is a supported integration (Modal, Blaxel, E2B, Docker), not an in-process default. — [smolagents](https://huggingface.co/docs/smolagents/en/index)

### Inferences
- Table stakes for a "real" loop in 2026 vendor SDKs: the runtime, not the app, repeats model to tools until a stop; the app consumes a stream of typed events; approvals pause with a serializable token and resume without re-implementing the loop; mutating tools are serialized relative to reads; denials and tool errors are model-visible results.
- Two approval shapes coexist. In-process callbacks (`canUseTool`, `on_approval`, Pydantic in-process guards) fit CLIs. Durable interruptions (`RunState`, `DeferredToolRequests`, LangGraph checkpoints, Mastra snapshots, Vercel approval parts) fit HTTP and queues. Docs that discuss production explicitly prefer the durable shape and tell you not to trust a client-supplied snapshot.
- "Structured output" is a loop exit and a retry budget (Claude `error_max_structured_output_retries`, Vercel `output` schema, OpenAI programmatic-tool output schemas), not a separate harness.

### Gaps
- Exact parallel-tool scheduling inside the OpenAI Python `Runner` (max concurrency, ordering of mixed hosted and local calls) was not on the tools or HITL pages opened.
- Microsoft approval behavior beyond the decorator/wrapper (streaming pause shape, sticky approvals, serialization) was only in the docs-repo extract, not a fully rendered Learn page.
- Gemini CLI was not confirmed to expose an embeddable tool-approval loop; see the MCP section.
- Codex SDK thread event schema (streaming tool events vs a single `run()` result) was not recovered; fetches of the current Codex SDK URL returned site navigation, not the article body. The older indexed page only showed `thread.run()` and resume-by-id. — [Codex SDK index hit](https://developers.openai.com/codex/sdk)

## Sandboxes and hosted execution (containers, code interpreter, computer use)

### Takeaway
Hosted execution is a product split: OpenAI and Anthropic will run the computer for you (containers, code interpreter, managed sandboxes) or hand you a local executor interface. Most other SDKs do not sandbox; they expect the application to, or they integrate a third-party sandbox.

### Cited Findings
- Claude Agent SDK runs a bundled Claude Code binary in the caller's process. `sandbox` / `SandboxSettings` is a first-class `ClaudeAgentOptions` field. `bypassPermissions` cannot be used as root on Unix and is documented for CI, containers, or other isolation. Managed Agents, a different product, runs the loop in an Anthropic cloud sandbox or a self-hosted sandbox. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview); [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop); [Python options extract](https://code.claude.com/docs/en/agent-sdk/python.md)
- OpenAI Agents SDK `CodeInterpreterTool` executes on OpenAI servers. `ShellTool` with `environment.type = container_auto` (optional `network_policy` `disabled` or `allowlist`, `file_ids`, `memory_limit`, `skills`) or `container_reference` is hosted. Local `ShellTool` takes an `executor` the application supplies; the SDK states that approval is not a sandbox. `ComputerTool` and `ApplyPatchTool` always run in the application's environment. Programmatic tool calling is a separate hosted V8 sandbox that cannot touch the filesystem or network. — [Tools](https://openai.github.io/openai-agents-python/tools/)
- Agents API (managed Codex harness) execution environments documented in the nav and comparison table: OpenAI-hosted sandbox, self-hosted sandbox, or no sandbox. The comparison table lists tool execution as service-connected tools, application function handlers, and an optional sandbox. A March 2026 OpenAI post describes Responses API orchestration plus the shell tool plus a hosted container plus skills plus compaction as the pieces that "make" an agent, and states the model only proposes tool calls. — [Agents](https://developers.openai.com/api/docs/guides/agents); [Equipping Responses API with a computer environment](https://openai.com/index/equip-responses-api-computer-environment/)
- Responses shell docs: hosted containers are managed by OpenAI; local shell mode is a runtime you host. Preinstalled languages cited on one indexed copy include Python 3.11 and Node.js 22.16; model names in examples differ across mirrors (`gpt-5.4`, `gpt-5.6`, `gpt-6-astra`), so the tool surface is the stable fact, not a single model id. — [Shell](https://developers.openai.com/api/docs/guides/tools-shell)
- smolagents documents secure code execution for `CodeAgent` via Modal, Blaxel, E2B, or Docker as the way "to make it secure," implying in-process exec is the unsafe default. — [smolagents](https://huggingface.co/docs/smolagents/en/index)
- Vercel docs say an experimental sandbox passed to the agent is not applied automatically: the tool implementation must delegate into it, and the sandbox description is not injected into the prompt unless the app adds it. — [Building agents](http://sdk.vercel.ai/docs/agents/building-agents)
- ADK, Mastra, LangGraph, Pydantic AI, and Microsoft Agent Framework pages opened here do not ship a built-in OS sandbox. Pydantic's durable-execution integrations (Temporal, DBOS, Prefect, and others) persist activities across process death; that is durability, not isolation. — [Pydantic capabilities overview extract](https://pydantic.dev/docs/ai/capabilities/overview/index.md)

### Inferences
- "Computer use," "shell," and "apply_patch" are now named hosted tool types on the OpenAI side, with a local-executor twin so the same model tool schema can run on your machine. A harness that only has `function_call` plus an app-side shell is the older shape; the newer shape is a typed computer/shell/patch protocol plus an environment handle (`container_auto` / `container_reference`).
- Isolation is still mostly outside the embeddable SDK except for OpenAI hosted containers, Anthropic Managed Agents, Claude's sandbox settings around the Claude Code binary, and smolagents' explicit sandbox backends.

### Gaps
- Claude `SandboxSettings` field list was named on the Python options page extract but the field schema itself was not opened.
- OpenAI Agents API sandbox security page (`/api/docs/guides/agents-api/environments/security`) was visible in navigation during a Codex docs fetch but the body was not retrieved.
- No opened Microsoft Foundry page described a hosted code-interpreter or computer-use primitive; only MCP tools and per-function approval were confirmed.

## Session persistence, handoffs, subagents, tracing

### Takeaway
Session memory, a durable pause token, and tracing spans are SDK features in the OpenAI and Claude stacks. Subagents are either a tool the parent model calls (Claude, OpenAI agents-as-tools, Codex) or a graph/workflow node (ADK, LangGraph, Mastra). Handoffs that replace the active agent and drop or filter history are an OpenAI-specific primitive.

### Cited Findings
- Claude sessions: capture `session_id` from `ResultMessage` (and the init `SystemMessage`) to resume. Resume restores prior context. Fork branches without modifying the original. `ClaudeSDKClient` tracks session ids across calls in Python. For stateless hosts, `session_store` / `sessionStore` mirrors transcripts to an app backend, but the subprocess still writes local disk first (dual-write). Subagents start with a fresh conversation; they load their own system prompt and project context such as `CLAUDE.md`, do not see the parent's turns, and only the final response returns to the parent as a tool result. Subagent spend counts toward `maxBudgetUsd`. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Claude `AgentDefinition` fields include `description`, `prompt`, optional `tools`, `disallowedTools`, model, `skills` preloaded at startup, `memory` (`user` | `project` | `local`), `mcpServers`, `permissionMode`, and `effort`. Omitting `tools` inherits the subagent tool set; listing tools restricts it. Permission mode inheritance is constrained: a subagent does not inherit `bypassPermissions` just because a field is set, except when the parent itself is in that mode (Claude Code v2.1.267+). — [Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- OpenAI sessions are a client-side memory primitive. Before each run the runner loads history and prepends it; after the run it stores new items (user, assistant, tool calls). A session cannot be combined in the same run with `conversation_id`, `previous_response_id`, or `auto_previous_response_id`. Built-ins named on the sessions page: `SQLiteSession`, `AsyncSQLiteSession`, `RedisSession`, `SQLAlchemySession`, `MongoDBSession`, `DaprSession`, `OpenAIConversationsSession`, `OpenAIResponsesCompactionSession`, `AdvancedSQLiteSession` (branching and usage analytics), `EncryptedSession` (wrapper with TTL). `SessionSettings(limit=N)` fetches only the last N items. `RunConfig.session_input_callback` can prune what the model sees without rewriting storage. Resume-after-approval must reuse the same session id and backend. `SQLiteSession` trusts the database file; the page's trust-boundary section was truncated. — [Sessions](https://openai.github.io/openai-agents-python/sessions/)
- OpenAI HITL says serialized `RunState` includes execution state, approvals, pending tool calls, arguments, usage, nested agent-as-tool resumptions, and trace metadata. `from_json` does not authenticate the snapshot. Production guidance: keep the snapshot on the server, send the reviewer only authorized tool details and opaque ids, authenticate the reviewer in app middleware, and atomically consume each pending request so replay cannot resume twice. — [Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)
- OpenAI handoffs transfer the conversation to another agent, which sees the full history unless an `input_filter` rewrites `HandoffInputData`. A built-in filter removes tool items (`handoff_filters.remove_all_tools`). Input guardrails stay on the first agent; output guardrails on the agent that finishes. Handoffs are not function tools, so tool guardrails do not apply to the handoff call. Default tracing wraps each handoff in `handoff_span()`. — [Handoffs](https://openai.github.io/openai-agents-python/handoffs/); [Tracing](https://openai.github.io/openai-agents-python/tracing/)
- OpenAI default tracing (Python and JS) wraps the whole `Runner.run` / `run_streamed` in a trace, plus spans for task, turn, agent, generation, function tool, guardrail, and handoff. Python also spans transcription, speech, and speech groups. Traces go to the OpenAI Traces dashboard; custom events are supported. JS docs say each turn span records turn number, agent name, and token counts including cached input and cache writes. — [Tracing (Python)](https://openai.github.io/openai-agents-python/tracing/); [Tracing (JS)](https://openai.github.io/openai-agents-js/guides/tracing/)
- Agents API vs SDK state: Agents API saves session configuration, turns, and items and includes automatic context compaction, multi-agent orchestration, programmatic tool calling, and MCP. Agents SDK state is "your storage and SDK sessions, or Responses conversation state." — [Agents](https://developers.openai.com/api/docs/guides/agents)
- Codex SDK is a separate TypeScript library (`npm install @openai/codex-sdk`, Node 18+) that controls local Codex threads: `startThread()`, `thread.run(prompt)`, further `run()` on the same thread, or resume by thread id. Docs say to use it for coding-focused Codex threads; if Codex is one specialist in a broader workflow, run Codex CLI as an MCP server and orchestrate with the Agents SDK. Codex subagent docs (product, not the SDK reference) describe parallel specialized agents that return summaries so the main thread stays small, with per-agent model and reasoning settings. — [Codex SDK](https://developers.openai.com/codex/sdk); [Subagents](https://developers.openai.com/codex/concepts/subagents)
- ADK separates short-term session state (`SessionService`: in-memory, `DatabaseSessionService` for SQL, and cloud-managed sessions after deploy to Vertex AI Agent Engine) from long-term `MemoryService` (`add_session_to_memory`, `search_memory`, tool `load_memory`). State key prefixes `user:` and `app:` persist across sessions; other state is session-local. `AdkApp` uses in-memory sessions locally and managed sessions when deployed. — [Memory](https://google.github.io/adk-docs/sessions/memory); [Vertex ADK develop](https://docs.cloud.google.com/agent-builder/agent-engine/develop/adk); [Cloud blog on state prefixes](https://cloud.google.com/blog/topics/developers-practitioners/remember-this-agent-state-and-memory-with-adk)
- LangGraph persistence is the checkpointer keyed by `thread_id`. HITL does not work without it. The graph can resume from an error state because the checkpoint holds the full state. — [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md)
- Mastra workflow snapshots store step outputs, execution path, and suspended-step metadata in the configured storage provider and survive restarts. Workflow `state` (separate from step input/output) also persists across suspend/resume. — [Snapshots](https://mastra.ai/docs/workflows/snapshots); [Workflow state](https://mastra.ai/docs/workflows/workflow-state.md)
- Pydantic lists durable execution as a core capability: the same agent runs as Temporal/DBOS/Prefect/Restate (and other) activities so model and tool calls survive restarts. Message history plus `DeferredToolResults` is how a paused tool run continues. — [README / capabilities extracts](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/)

### Inferences
- "Session" means three different resources that docs now tell you not to conflate: client-side transcript stores (OpenAI `Session`, Claude JSONL plus optional `sessionStore`), server-side conversation ids (`conversation_id` / Conversations API / Agents API sessions), and sandbox/container ids. A harness that only keeps a message list in memory is behind the SDKs that ship at least one durable backend and a resume token.
- Subagent context isolation (fresh transcript, summary returned to parent) is documented as a context-window strategy by both Claude and Codex, not only as an org-chart feature.
- Tracing of every tool and handoff span is built into the OpenAI Agents SDK by default. Other stacks mostly point at external tracing (LangSmith, OpenTelemetry, Logfire) or leave it to the app. That default-on trace is part of what OpenAI calls the SDK, not an example.

- OpenAI JS session API parity with the Python backends was not verified; only JS tracing was opened.
- Codex SDK event types, approval hooks, and sandbox flags were not in the retrieved article body.
- ADK multi-agent transfer vs task-tool delegation was not opened; only session/memory and compaction pages were confirmed.
- No opened page gave a numeric retention or encryption requirement that all vendors share.

## Guardrails, hooks, middleware

### Takeaway
Hooks (Claude), guardrails (OpenAI, Pydantic), callbacks/plugins (ADK), and middleware (LangChain/LangGraph) are the same harness slot: deterministic code around the model and tool calls that can block, rewrite, or observe. They are SDK extension points, not model behavior.

### Cited Findings
- Claude hooks are callbacks the application (not the model) runs. Events confirmed on the hooks page include `PreToolUse` (can block or modify), `PostToolUse`, `PostToolUseFailure`, `PostToolBatch` (TypeScript only), `UserPromptSubmit`, `Stop`, `SubagentStart`, plus TypeScript-only `SessionStart`, `SessionEnd`, `PreCompact` is described on the agent-loop page (trigger `manual` or `auto`), `StopFailure`, `TaskCreated`, `TaskCompleted`, `Elicitation` / `ElicitationResult` for MCP user input, `ConfigChange`, `InstructionsLoaded`. `PostToolBatch` fires once per tool batch before the next model call. Python `ClaudeSDKClient` can register hooks as Python functions; `query()` alone is documented as not enabling custom tools and hooks the way the client does. — [Hooks](https://code.claude.com/docs/en/agent-sdk/hooks.md); [PyPI package text](https://pypi.org/project/claude-agent-sdk/); [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- OpenAI guardrails: input, output, and tool input/output. They run "alongside" the agent and tripwire. Tool guardrails attach to a function tool or to every tool from a local MCP server. The runner records `guardrail_span`s. `RunConfig.tool_error_formatter` customizes the model-visible rejection string. — [Guardrails](https://openai.github.io/openai-agents-python/guardrails/); [Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/); [Tracing](https://openai.github.io/openai-agents-python/tracing/)
- ADK callbacks (`before_model`, and tool/agent equivalents) are per agent or per tool and can observe or replace the model call. Plugins (`BasePlugin`, ADK Python v1.7.0 and other language versions cited) register once on the `Runner` and apply to every agent, tool, and LLM call. Docs explicitly say to prefer plugins over callbacks for security guardrails. Shipped plugin examples named on the page include BigQuery analytics, context filter, and global instruction. — [Callbacks](https://google.github.io/adk-docs/callbacks/); [Plugins](https://google.github.io/adk-docs/plugins/)
- Pydantic `ToolGuardrail` outcomes include block (model sees refusal text), retry (`ModelRetry`; output-side retry re-runs the tool, so side effects already happened), and approve (raises `ApprovalRequired` and joins the deferred-tool path). External/deferred tools are rejected before execution hooks, so a guard cannot vet them; the application that executes them must. Hidden-tool filtering does apply to definitions before the call. — [Guardrails](https://pydantic.dev/docs/ai/harness/guardrails/)
- LangChain JS `humanInTheLoopMiddleware` is middleware on `createAgent`, not a separate server. Deep Agents documents `PatchToolCallsMiddleware` repairing history if a run is cancelled before a tool result. — [JS human-in-the-loop](https://docs.langchain.com/oss/javascript/langchain/human-in-the-loop); [Deep Agents HITL](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop)
- Vercel `toolApproval` functions are the policy slot. A separate `@ai-sdk/policy-opa` package is named for policy-as-code. That package was not opened. — [Tool approvals](https://sdk.vercel.ai/docs/agents/tool-approvals)

### Inferences
- A production harness in these SDKs has at least one pre-tool interceptor that can deny or rewrite arguments before execution, and a post-tool interceptor for audit. Claude's hook catalog is the widest (session lifecycle, compaction, subagents, MCP elicitation). OpenAI and Pydantic fold the same idea into guardrails plus approval. ADK splits local callbacks from global plugins and tells you to put policy in the global layer.
- Output guardrails that retry a tool after it has already run are documented as unsafe for side effects (Pydantic). The harness primitive is "decide before execute," not "undo."

### Gaps
- Full Claude hook payload schemas and whether Python supports every TypeScript event were not opened beyond the availability table in the hooks extract.
- OpenAI Agents SDK lifecycle hooks other than guardrails (the `ref/lifecycle` page listed in llms.txt) were not opened, so it is unclear whether they match Claude's pre/post tool hooks or are only tracing callbacks.
- Mastra agent-level guardrail middleware, as opposed to workflow suspend, was not opened.
- No opened page stated a required hook set for "production" in the form of a checklist that all vendors share.

## MCP, skills, memory, compaction

### Takeaway
MCP is a standard tool bus in every major SDK opened here, usually with an allow-list and sometimes deferred schema loading. Skills are filesystem or hosted bundles of instructions plus resources, not just longer prompts. Compaction (summarize old turns) is now a built-in in Claude, OpenAI, ADK, and the managed Agents API, not an application trick.

### Cited Findings
- Claude MCP: servers are stdio processes, HTTP, or in-process SDK MCP servers. Tool names are prefixed `mcp__<server>__<tool>`. `allowedTools` accepts wildcards (`mcp__github__*`). Tool search defers MCP schemas by default and falls back to loading all schemas on unsupported models. Custom tools are in-process MCP servers (`@tool` plus `create_sdk_mcp_server` / `createSdkMcpServer`). — [MCP](https://platform.claude.com/docs/en/agent-sdk/mcp); [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop); [PyPI](https://pypi.org/project/claude-agent-sdk/)
- Claude skills are files on disk, not a programmatic register API. Discovery follows setting sources: user `~/.claude/skills/`, project `.claude/skills/`, and parent directories up to the repo root, plus `--add-dir` directories. `skills` option is `"all"`, a name list, or `[]`. The SDK rejects wildcard skill names (Python SDK 0.2.129+). Setting `skills` adds the `Skill` tool to `allowedTools`. Skill descriptions load at session start; full body loads when invoked. Subagents can preload named skills. Plugins package skills, agents, hooks, and MCP servers by local path. Memory and `CLAUDE.md` load like Claude Code; the compactor re-reads `CLAUDE.md`, so persistent rules belong there rather than only in the first user message. — [Skills](https://code.claude.com/docs/en/agent-sdk/skills); [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop); [Overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Claude compaction is automatic near the context limit. The stream emits `system` / `compact_boundary`. Older messages are replaced by a summary. `PreCompact` can archive the transcript. The app can send `/compact`. Subagents are the other context tool: parent context grows by the summary only. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- OpenAI Agents SDK MCP is a documented primitive (`MCP server tool calling` on the overview). Local servers can carry tool guardrails and `require_approval`. `HostedMCPTool` can set `defer_loading` and `require_approval` (`always` / `never`). Sticky hosted-MCP approvals key on `server_label` plus tool name. — [Overview index](https://openai.github.io/openai-agents-python/); [Tools](https://openai.github.io/openai-agents-python/tools/); [Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)
- OpenAI skills attach to hosted or local shell environments as `skill_reference` (`skill_id`, `version`) or inline bundles (`environment.skills`). Platform docs list a Skills guide next to tool search and programmatic tool calling as cross-runtime features whose lifecycle differs by API. — [Tools](https://openai.github.io/openai-agents-python/tools/); [Agents](https://developers.openai.com/api/docs/guides/agents)
- OpenAI compaction: `OpenAIResponsesCompactionSession` wraps another session and calls `responses.compact`. Auto mode runs after the turn if `should_trigger_compaction` says so, and streaming waits for it before the iterator closes. Modes: `previous_response_id`, `input` (rebuild from session items), and default `auto`. Do not wrap `OpenAIConversationsSession` with it. `ModelSettings(store=False)` forces input mode because the response chain is not stored. Compaction failure attempts to restore the previous history. Agents API separately claims automatic context compaction as a managed-harness feature. Responses API navigation lists a compaction guide. — [Sessions](https://openai.github.io/openai-agents-python/sessions/); [Agents](https://developers.openai.com/api/docs/guides/agents)
- ADK `MCPToolset` discovers tools (`list_tools`), adapts schemas to `BaseTool`, and proxies `call_tool`. Compaction is `EventsCompactionConfig` on `App` (Python/Java/Kotlin) or `contextCompactors` on `LlmAgent` (TypeScript), implemented in `SingleFlow` via `CompactionRequestProcessor`. Strategies: token threshold plus `event_retention_size`, and sliding window `compaction_interval` plus `overlap_size`. If both are set, token-based wins and sliding window is skipped that turn. Optional `LlmEventSummarizer` / `LlmSummarizer` picks the summarizer model and prompt. Supported versions cited: Python v1.16.0, Java v0.2.0, TypeScript v0.6.0, Kotlin v0.7.0. Context caching (`ContextCacheConfig`: `min_tokens`, `ttl_seconds`, `cache_intervals`) is a separate App-level feature from compaction. — [MCP tools](https://google.github.io/adk-docs/tools/mcp-tools); [Compaction](https://adk.dev/context/compaction/); [Context caching](https://google.github.io/adk-docs/context/caching/)
- Gemini CLI extensions are a packaging format, not a general agent SDK. A directory with `gemini-extension.json` can declare `mcpServers`, `contextFileName` (for example `GEMINI.md`), `excludeTools`, and a plan directory. Extensions install into the CLI; same-named MCP servers in `settings.json` win. Docs describe examples `context`, `custom-commands`, `exclude-tools`, and `mcp-server`. This is an extension model for the Gemini CLI product. — [Extensions](https://geminicli.com/docs/extensions); [Extension reference](https://github.com/google-gemini/gemini-cli/blob/main/docs/extensions/reference.md)
- Microsoft Agent Framework MCP clients pass custom headers (`static_headers` or per-run `header_provider`). Headers are origin-bound and stripped on cross-origin redirects. Dynamic identity changes reconnect and refresh tool discovery. Host payloads are capped at 1 MiB by default (`max_host_payload_size_bytes`); oversized payloads are dropped from the host channel but the parsed result still reaches the model. `tool_result_content` selects `structuredContent` vs `content` for the model (`structured_first` default). MCP sampling/`sampling_callback` is deprecated as of MCP spec 2026-07-28 and scheduled for removal no later than 2027-07-28. Docs tell you to log data sent to remote MCP servers and prefer first-party hosts over proxies. — [Using MCP Tools](https://learn.microsoft.com/en-us/agent-framework/agents/tools/local-mcp-tools)
- Vercel `@ai-sdk/mcp` `createMCPClient().tools()` converts MCP tools into AI SDK tools for `generateText` / `streamText`. HTTP transport options include `initialSessionId`, `onSessionIdChange`, `onSessionExpired`, and `terminateSessionOnClose`. Protocol note in the npm text: legacy versions via `initialize`, and MCP `2026-07-28` via stateless discovery. Package version cited on the npm page: 2.0.62, published 2026-09-28. — [@ai-sdk/mcp](https://www.npmjs.com/package/%40ai-sdk%2Fmcp)
- smolagents loads tools from any MCP server via `ToolCollection.from_mcp`, and also from LangChain tools or a Hub Space. — [smolagents](https://huggingface.co/docs/smolagents/en/index)
- Pydantic capabilities list (extract) includes an Ask User harness capability, tool approval, deferred-call handling, system reminders, and durable execution. Memory as a separate long-term store was not confirmed on the pages retrieved. — [Capabilities overview](https://pydantic.dev/docs/ai/capabilities/overview/index.md)
- ADK long-term memory is explicit: `InMemoryMemoryService` (keyword search, lost on restart) versus other `MemoryService` implementations; ingestion is usually of a completed session, retrieval is a tool (`load_memory` / `PreloadMemoryTool` on Vertex). — [Memory](https://google.github.io/adk-docs/sessions/memory); [Vertex develop](https://docs.cloud.google.com/agent-builder/agent-engine/develop/adk)

### Inferences
- MCP plus an allow-list (`allowedTools`, `allowed_tools`, `excludeTools`, `require_approval`) is table stakes. Deferred tool schemas (Claude tool search, OpenAI `defer_loading` / namespaces) are the 2026 answer to large MCP surfaces blowing the context window.
- Skills converged on a file or hosted bundle that is discovered, summarized into the prompt, and fully loaded on invoke (Claude filesystem skills, OpenAI shell `skill_reference`). An SDK that only accepts a system-prompt string has no skill primitive.
- Compaction is a runtime feature with a trigger (token threshold or turn interval), a retention tail, a summary event the client can observe, and a warning that early instructions are not durable unless re-injected (Claude `CLAUDE.md`, ADK summarizer). Wrapping a session with a compactor (`OpenAIResponsesCompactionSession`) is the SDK pattern when the store and the compactor are different components.

### Gaps
- OpenAI Skills guide body (what a skill file contains, mount path, versioning rules) was not opened; only the SDK `ShellToolSkillReference` shape and the index link were confirmed.
- Responses API `responses.compact` request fields were not opened.
- Mastra agent memory (threads/resources appeared in a network-approval sample) was not documented here beyond workflow snapshots.
- LangGraph long-term store vs checkpointer was not opened; only the checkpointer requirement for interrupts was confirmed.
- Gemini CLI was not shown to be an embeddable library with sessions or compaction. Treat it as a CLI extension manifest unless a later source says otherwise.
- Microsoft Agent Framework session store and Foundry hosted-agent session APIs were not opened.

## What their docs say a minimal production harness must include

### Takeaway
No vendor publishes one universal checklist. Each documents a minimum runtime for its own loop, and the overlapping production requirements are: a bounded tool loop, an approval gate that fails closed, a durable session or checkpoint, isolation around shell/computer, and traces or cost accounting.

### Cited Findings
- Claude's own capability table is the product's definition of the harness: built-in tools, hooks, subagents, MCP, permissions, sessions, skills/commands/memory, plugins. The loop page says a budget cap is "a good default for production agents" because unbounded loops run until the model stops. `ResultMessage` always carries `total_cost_usd`, `usage`, `num_turns`, and `session_id` even on error subtypes (with an exception noted for some crashes whose cost fields may be zeroed; the page was truncated mid-sentence). Persistent rules belong in `CLAUDE.md` because compaction drops early prompt text. `bypassPermissions` is restricted to isolated environments. — [Overview](https://code.claude.com/docs/en/agent-sdk/overview); [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- OpenAI's overview calls the minimal primitive set agents, handoffs, and guardrails, and then lists what the SDK adds for real applications: function tools, MCP, sessions, human-in-the-loop, and tracing aimed at debugging and evaluation. The HITL page's production rules are operational: do not deserialize untrusted `RunState`; keep approval state server-side; authenticate the reviewer; consume each interruption atomically. Shell docs say always sandbox, allow/deny commands, and log tool activity. The Agents guide tells you to pick exactly one state mechanism (Agents API session, SDK session, Responses conversation, or manual history) and follow that runtime's cleanup. — [Overview](https://openai.github.io/openai-agents-python/); [Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/); [Shell](https://developers.openai.com/api/docs/guides/tools-shell); [Agents](https://developers.openai.com/api/docs/guides/agents)
- OpenAI's managed Agents API is described as the low-integration option when OpenAI should run the harness: compaction, multi-agent orchestration, programmatic tool calling, MCP, and a sandbox choice (hosted, self-hosted, or none). That is a hosted harness, not application code. — [Agents](https://developers.openai.com/api/docs/guides/agents)
- LangGraph docs: HITL requires a checkpointer and a `thread_id`; "use a durable checkpointer in production." `MemorySaver` is the example, not the production store. — [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md); [JS HITL](https://docs.langchain.com/oss/javascript/langchain/human-in-the-loop)
- Vercel positions `ToolLoopAgent` as the production agent abstraction because it owns the loop, stopping conditions, and approvals. Default stop is 20 steps. Provider-executed tools are outside that approval gate, which the docs state explicitly so callers do not assume the gate is universal. — [Building agents](http://sdk.vercel.ai/docs/agents/building-agents); [ToolLoopAgent source](https://github.com/vercel/ai/blob/main/packages/ai/src/agent/tool-loop-agent.ts)
- ADK's documented stack for a running agent is `App` or `Runner` plus a `SessionService`, optional `MemoryService`, optional `EventsCompactionConfig`, optional plugins for policy, and `MCPToolset` when tools are remote. Compaction is motivated as latency and cost control, not as an optional demo. Vertex deployment swaps in managed sessions. — [Compaction](https://adk.dev/context/compaction/); [Memory](https://google.github.io/adk-docs/sessions/memory); [Plugins](https://google.github.io/adk-docs/plugins/)
- Microsoft's MCP page is the closest "production must" text found: you are responsible for third-party MCP data handling; review and track servers; log shared credentials; prefer servers hosted by the service itself; use a specific Azure credential rather than `DefaultAzureCredential` in production; cap host payloads. Approval is a per-tool flag, not a global mode in the extract. — [Using MCP Tools](https://learn.microsoft.com/en-us/agent-framework/agents/tools/local-mcp-tools)
- smolagents' security requirement for code agents is an external sandbox (Modal, Blaxel, E2B, or Docker). The library itself is intentionally a thin loop ("~thousand lines"). — [smolagents](https://huggingface.co/docs/smolagents/en/index)
- Pydantic's production path in the retrieved docs is durable execution plus deferred tool approval, not a bundled coding sandbox. The same agent object is what runs in the workflow engine. — [Capabilities overview](https://pydantic.dev/docs/ai/capabilities/overview/index.md)
- A March 2026 OpenAI engineering post states a concrete composition for a long-running computer-using agent on the Responses API: orchestration (Responses), shell tool, hosted container, skills, and compaction. It also states the model cannot execute tools itself. That is vendor architecture guidance, not a cross-SDK standard. — [Equipping Responses API with a computer environment](https://openai.com/index/equip-responses-api-computer-environment/)

### Inferences
- Where docs talk about production at all, the shared minimum is: (1) a loop with an explicit stop (turns, steps, or budget), (2) a fail-closed approval decision stored with the run, (3) a session or checkpoint that survives process restart, (4) sandboxing for shell and computer use, (5) usage or tracing on every run, (6) compaction or an equivalent context bound for long sessions, (7) MCP behind an allow-list. Items (4) and (6) are strongest in the coding-agent products (Claude Agent SDK, Codex/Agents API, OpenAI shell) and optional or absent in general tool-calling SDKs (Vercel, Pydantic, smolagents-without-sandbox, Microsoft's tool wrapper).
- Several docs distinguish the primitive from the app's job. The SDK pauses and records; the app authenticates the human, chooses the sandbox, and picks the session backend. Treating any of those as "just prompt the model to be careful" is contradicted by the approval and sandbox pages.

### Gaps
- No opened document from Anthropic, OpenAI, Google, or Microsoft is titled as a cross-vendor "minimal production harness" spec. The lists above are each product's own primitives plus the sentences where they say "production" or "always."
- Deployment checklists linked from OpenAI navigation (`/api/docs/guides/deployment-checklist`, `/api/docs/guides/production-best-practices`, Agents API architecture) were not fetched.
- Codex SDK production requirements (sandbox mode, approval policy, thread storage) remain unverified because the live page body did not render.
- Cost of compaction (extra model call, whether it is itself approval-gated) is described for OpenAI sessions (usage is added to the run) but not quantified for Claude or ADK beyond "summarize with an LLM."
