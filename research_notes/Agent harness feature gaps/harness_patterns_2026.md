# Agent harness patterns that became expected in 2025–2026

Scope is the pattern, not a product inventory. Every claim below comes from a page fetched in full (or the portion the fetch returned before truncation). Search snippets that were not opened are not used as evidence. “As of 2026-09-29” means the pages were retrieved on that date; several vendor docs are living pages without a visible publish date.

Products with opened primary pages: Claude Code docs (sandboxing, permission modes, hooks guide), Cursor (sandbox engineering post; changelog 2.5, 17 Feb 2026), OpenAI Codex (engineering post, 23 Jan 2026), Gemini CLI (`docs/cli/sandbox.md` on `main`), the MCP authorization spec dated 2025-11-25, and BleepingComputer’s 20 Jul 2026 report of Pillar Security’s sandbox-escape series.

## Which of these are widely shipped by at least three serious products in 2026?

### Takeaway
OS-enforced shell/filesystem sandboxing, a separate allow/ask/deny (or equivalent) approval layer, MCP as a tool-extension bus, and packaged skills are the patterns with opened evidence from at least three serious coding-agent products. Plan-before-edit is shipped as a real permission mode by Claude Code and Cursor and as an in-loop plan tool by Codex, so the *idea* is widespread but the *enforcement* is not the same thing.

### Cited Findings
- Claude Code’s Bash sandbox runs on macOS via Seatbelt with nothing to install, and on Linux and WSL2 via bubblewrap (filesystem) plus socat (network proxy). Native Windows is unsupported; Windows users are told to run inside WSL2. Sandboxed commands can write the working directory, a per-user temp dir, and `--add-dir` paths; the OS enforces the boundary for Bash, PowerShell, and Monitor commands and their children. If dependencies are missing, the default is a warning and unsandboxed execution unless `sandbox.failIfUnavailable` is true. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing.md)
- Cursor rolled out agent sandboxing on macOS, Linux, and Windows. macOS uses Seatbelt (`sandbox-exec`) with a dynamically generated profile (they rejected App Sandbox, containers, and VMs). Linux uses Landlock plus seccomp directly, with an overlay so `.cursorignore` files can be made unreadable. Windows runs that Linux sandbox inside WSL2; they say a native Windows sandbox is significantly harder and that they are working with Microsoft on primitives. Sandboxed agents “stop 40% less often” than unsandboxed ones, and “a third of requests on supported platforms” run with the sandbox. — [Cursor sandbox engineering post](https://cursor.com/blog/agent-sandboxing)
- Gemini CLI sandboxing is selectable by `-s` / `--sandbox`, `GEMINI_SANDBOX`, or `tools.sandbox` in settings. Methods documented: macOS Seatbelt profiles (`permissive-open` default through `strict-proxied`), Docker or Podman (default image `ghcr.io/google/gemini-cli:latest`, workspace bind-mounted at the same absolute path), a Windows-native sandbox that sets Low integrity via `icacls`, Linux gVisor/`runsc` (explicit only, not auto-detected), and LXC/LXD. There is also per-tool sandboxing for `shell_exec` and `write_file`, plus a “Sandbox Expansion Request” modal when a command needs extra paths or network. — [Gemini CLI sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- Codex’s harness puts a developer message in the prompt that describes the sandbox for the Codex-provided `shell` tool only: file permissions, network access, when to ask, and writable folders. The same post states that other tools, “such as those provided from MCP servers, are not sandboxed by Codex and are responsible for enforcing their own guardrails.” Changing sandbox configuration, approval mode, or cwd mid-conversation is done by appending a new message so the prompt prefix stays cacheable. — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- BleepingComputer (20 Jul 2026) treats sandboxes as already shipping in Cursor, Codex, Gemini CLI, and Google Antigravity, and describes the shared design line as “the agent is trusted inside the project workspace, the host outside is protected.” — [BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/)
- Claude Code permission modes are a separate axis from the sandbox: `default` (reads only; UI label Manual), `acceptEdits`, `plan`, `auto` (a second classifier model), `dontAsk` (deny anything that would prompt; documented for CI), and `bypassPermissions`. Deny rules apply in every mode, including bypass. As of v2.1.283, auto is the built-in start mode for interactive terminal and VS Code sessions. Rule syntax and modes are layered: modes set the baseline; allow/ask/deny rules sit on top. — [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md)
- Cursor changelog 2.5 (17 Feb 2026) adds granular sandbox network controls (`sandbox.json`: user allowlist only, allowlist plus defaults, or allow all), enterprise admin allowlists/denylists, and states that Ask mode keeps a read-only sandbox even if “Run everything” is enabled. The sandbox post says agents are taught, via the Shell tool description and failure rendering, when to request elevated permissions. — [Cursor changelog 2.5](https://cursor.com/changelog/2-5); [Cursor sandbox post](https://cursor.com/blog/agent-sandboxing)
- Codex exposes both a sandbox description and an approval policy in the prompt (the bundled snippets named in the post are `workspace_write.md` and `on_request.md`). — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Plan mode in Claude Code blocks source edits until the user approves a plan. Claude may still read files and run shell commands; what happens to those commands depends on whether auto mode’s classifier is available (`useAutoModeDuringPlan` defaults on). Entry is `Shift+Tab`, `/plan`, or `--permission-mode plan`. Approval options include continuing in auto mode, approving edits manually, or keeping planning. `AskUserQuestion` is called out as a tool no permission mode auto-approves, including bypass. — [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md)
- Cursor Plan mode can hand execution to a Cloud Agent (“Build in Cloud”) while the user keeps working locally. The same release enforces a read-only sandbox for Ask mode. — [Cursor changelog 2.5](https://cursor.com/changelog/2-5)
- Codex ships a built-in `update_plan` tool (“Updates the task plan”) in the same tools array as `shell`, web search, and MCP functions. The post does not describe this as a permission mode that blocks edits. — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Skills are part of the Codex prompt: if any skills are configured, the user-instruction block includes a short preamble, per-skill metadata, and instructions for how to use them, placed with AGENTS.md content before the environment context. — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Claude Code’s hooks guide points to skills (“additional instructions and executable commands”), subagents (“tasks in isolated contexts”), and plugins (“packaging extensions to share across projects”) as the other extension mechanisms beside hooks. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide.md)
- Cursor 2.5 plugins “package skills, subagents, MCP servers, hooks, and rules into a single install,” with a marketplace and `/add-plugin`. Named initial partners include Amplitude, AWS, Figma, Linear, and Stripe. — [Cursor changelog 2.5](https://cursor.com/changelog/2-5)
- MCP tools are first-class in the Codex loop, namespaced like `mcp__weather__get-forecast`, and the post warns that honoring `notifications/tools/list_changed` mid-conversation changes the `tools` array and blows the prompt-cache prefix. — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Claude Code has product-level MCP elicitation: notification hook matchers include `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, and `elicitation_response`, and hook events include `Elicitation` and `ElicitationResult`. Hooks can also be type `mcp_tool`. Permission modes say connector tools an org set to `ask`, and MCP tools marked `requiresUserInteraction`, are not auto-approved in any mode. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide.md); [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md)
- The MCP authorization spec (protocol version 2025-11-25) makes authorization optional. HTTP transports that support it should use OAuth 2.1, protected-resource metadata (RFC 9728), and resource indicators (RFC 8707). STDIO “SHOULD NOT” follow this spec and should take credentials from the environment. Client ID metadata documents are the preferred registration path; dynamic client registration is a fallback. — [MCP authorization, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

### Inferences
- A 2026 harness that only has an allowlist of shell command strings, with no OS sandbox, is behind Claude Code, Cursor, Gemini CLI, and Codex. The three-product bar is met for “sandbox the shell, and still have an approval policy,” not for any one OS mechanism. Seatbelt on macOS shows up in Claude Code, Cursor, and Gemini CLI; bubblewrap is Claude Code’s Linux tool; Landlock+seccomp is Cursor’s; Docker/Podman/gVisor are Gemini CLI’s. There is no single sandbox primitive that all of them use.
- “Plan mode” as a permission posture (edits blocked until approval) is evidenced for Claude Code and Cursor. Codex’s `update_plan` shows planning as a tool the model updates, which is a weaker, different pattern. Counting Codex makes “a planning affordance” a three-product pattern; it does not make a read-only plan mode table stakes.
- Skills plus MCP are how these products extend the agent without forking the core loop. Plugins, where documented (Cursor marketplace; Claude’s plugin pointer), are a packaging layer over skills, hooks, MCP, and rules, not a separate capability.

### Gaps
- OpenCode and Block Goose were not opened. Search results suggested OpenCode has per-agent allow/ask/deny rules and a plan agent, and that Goose has skills and an experimental “code mode” MCP extension. Those are not treated as evidence here, so the “three products” count does not depend on them.
- Cursor and Codex hooks were not opened as specs. Cursor’s changelog only says plugins can contain hooks. Whether hooks are table stakes (three products with a real lifecycle API) is not established from opened pages; only Claude Code’s hook surface was read.
- Subagents are documented as shipped for Claude Code (hooks guide and permission-mode references to agent teams / `SendMessage`) and Cursor (async subagents that can spawn subagents). A third product’s subagent doc was not opened (Codex has a subagents URL in the docs nav that this fetch did not return body text for).
- No opened page documents checkpoints, rewind, or session replay as a shipped capability.
- Computer use / browser control, OpenTelemetry, cost accounting, and a JSON-RPC embedding API were not confirmed from an opened page body. Claude Code does document a headless `-p` path and `dontAsk` for CI, which is one product, not three. Codex’s docs nav lists App Server, non-interactive mode, GitHub Action, hooks, worktrees, and computer use; the fetch of the AGENTS.md URL returned a navigation shell, not those articles.

## Which are still rare or explicitly experimental?

### Takeaway
Explicitly experimental or platform-incomplete items in opened primary docs are Gemini CLI’s LXC sandbox, Claude Code’s agent-typed hooks, native Windows sandboxing (absent in Claude Code, WSL2-only in Cursor), and anything that depends on MCP authorization, which the spec marks optional and stdio is told not to use. Agent teams, background process supervision, auto-memory, and desktop control cannot be classified as rare versus common because the primary pages for them were not opened.

### Cited Findings
- Gemini CLI documents LXC/LXD sandboxing as “Linux only, experimental.” The container must already exist and be running; Gemini does not create it. It is aimed at tools that need a full system (Snapcraft, Rockcraft), not at the default path. gVisor/`runsc` is supported but “not auto-detected.” — [Gemini CLI sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- Claude Code hook types include `"agent"`: “multi-turn verification with tool access. Agent hooks are experimental and may change.” Command, HTTP, MCP-tool, and prompt hooks are listed without that experimental label. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide.md)
- Claude Code: “Native Windows is not supported.” On WSL2, launching a Windows binary (`cmd.exe`, `powershell.exe`, anything under `/mnt/c/`) is handed to the Windows host over a Unix socket, and blocking that requires the optional seccomp filter. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing.md)
- Cursor: “On Windows, we run our Linux sandbox inside WSL2.” They call a native Windows sandbox “significantly harder” because existing primitives target browsers. — [Cursor sandbox engineering post](https://cursor.com/blog/agent-sandboxing)
- Gemini CLI is the only opened product doc that describes a Windows-native mechanism, and it is mandatory-integrity (`icacls` Low), not a syscall sandbox. Integrity-level changes persist after the session; resetting them is a manual `icacls ... /setintegritylevel Medium`. — [Gemini CLI sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- MCP authorization “is OPTIONAL.” Stdio implementations “SHOULD NOT” follow the OAuth spec. Servers must implement protected-resource metadata only when they support the HTTP authorization flow. — [MCP authorization, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- Claude Code’s auto mode (a classifier model reviewing actions) is a shipped default for interactive sessions as of v2.1.283, but the same page says it “does not guarantee safety,” org admins can set `permissions.disableAutoMode` to `"disable"`, and it is unavailable for some model/provider combinations (the fetch truncated the provider matrix). `dontAsk` “never appears in the cycle” and is a CLI/settings choice aimed at CI. — [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md)
- Codex compaction via the Responses API `/responses/compact` endpoint, including an opaque `type=compaction` item with `encrypted_content`, is described as what Codex now does automatically past `auto_compact_limit`. An earlier design was a user-invoked `/compact` command that summarized into a new `input`. The post presents the server endpoint as the current path, not as experimental, but it is specific to Responses API semantics (stateless requests, ZDR, no `previous_response_id`). — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)

### Inferences
- “Experimental” in these docs means a named escape hatch (LXC, agent hooks), not the core sandbox or the core permission prompt. Classifier-based auto-approval is past experimental at Anthropic (it is the default) and is echoed by Cursor’s Ask vs other run modes only as a changelog behavior, not as a described classifier. Do not treat “auto-review classifier” as confirmed for three products.
- Native Windows containment is the clearest platform gap: two of the three sandbox writeups (Claude Code, Cursor) punt to WSL2. A harness that claims parity on Windows without WSL is ahead of those two, or is using a weaker mechanism like Gemini’s integrity level.
- MCP OAuth is spec-complete for HTTP and deliberately out of scope for stdio. Shipping stdio MCP without also shipping streamable HTTP plus OAuth is still compatible with the spec. Opened product pages show MCP tool calls and elicitation UI in Claude Code, and MCP tools in Codex; they do not show that OAuth, resources, prompts, or sampling are implemented by three coding agents.

### Gaps
- No opened page labels agent teams, subagents, skills, plan mode, or worktrees as experimental. A secondary writeup in search results claimed Claude Code agent teams sit behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; that page was not opened, and the official hooks guide treats `TeammateIdle` and agent-team messages as real events. Conflict unresolved.
- Codex CLI reference snippets in search marked `codex mcp`, `codex mcp-server`, and `codex sandbox` as “Experimental.” That reference page was not opened, so those maturity labels are not used.
- Streamable HTTP replacing HTTP+SSE, Tasks, and URL-mode elicitation showed up in search snippets for later MCP spec pages. Only the 2025-11-25 authorization document was opened, so transport evolution and sampling are gaps.
- Auto-memory, prompt caching outside Codex, OpenTelemetry, session replay, and computer use have no opened product doc here. Codex’s docs navigation lists Computer use, Record & Replay, Hooks, Git worktrees, and App Server, but those article bodies were not retrieved.

## What concrete limitations or incidents do primary sources describe?

### Takeaway
The failure mode primary sources actually describe is not “the syscall sandbox is broken.” It is that the agent is allowed to write workspace files that unsandboxed host components later trust (hooks, interpreters, Git metadata, Docker sockets), plus escape hatches the product itself documents (unsandboxed retry, command allowlists that match a name, MCP tools left outside the sandbox). Approval fatigue and sandbox-unaware retry loops are the usability failures vendors describe in their own posts.

### Cited Findings
- Pillar Security (Eilon Cohen, Dan Lisichkin, Ariel Fogel), as reported by BleepingComputer on 20 Jul 2026, reproduced escapes in Cursor, Codex, Gemini CLI, and Antigravity “without attacking the sandbox head-on.” The agent stays inside the sandbox and writes a file that a trusted tool outside later runs. They group seven findings into four modes: denylist sandboxes that cannot keep up with the OS, workspace config that is executable code, “safe” command allowlists that trust a command’s name rather than its arguments, and privileged local daemons outside the sandbox. Prompt injection in a README, issue, dependency, or diff is described as the trigger. — [BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/)
- Concrete bugs from that report: Cursor workspace `.claude` hook config became unsandboxed command execution, tracked as CVE-2026-48124, fixed in Cursor 3.0.0. A second Cursor bug let the agent edit a virtualenv interpreter that the editor’s Python extension ran during discovery. A third used Git metadata that does not live in a directory named `.git`, via fsmonitor, bypassing path rules; patched in 3.0.0, CVE pending. Codex CLI’s allowlist trusted `git show` by name when the invocation was not read-only; OpenAI patched it in v0.95.0, paid a high-severity bounty, CVE pending. One Docker-socket issue hit Codex, Cursor, and Gemini CLI; reported fixed. Google classified two Antigravity findings (a macOS Seatbelt denylist bypass and a `.vscode` task-config bypass of Secure Mode) as “Other valid security vulnerabilities” and downgraded them as hard to exploit because they need social engineering or a user trusting a repo that contains an indirect prompt injection. — [BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/)
- The same article says the class is older: in April, Cymulate documented “Configuration-Based Sandbox Escape” across Claude Code, Gemini CLI, and Codex CLI, where a file written inside the sandbox runs on the host at the next launch. That Cymulate post was not opened; this is BleepingComputer’s attribution. — [BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/)
- Claude Code documents its own unsandboxed retry: on a sandbox violation the model may retry with `dangerouslyDisableSandbox`, which runs outside the sandbox and goes through the normal permission flow (a prompt in Manual mode, the classifier in auto mode). Strict mode is `allowUnsandboxedCommands: false`. The docs also warn that `sandbox.filesystem.disabled: true` leaves network allowlisting but gives unrestricted host filesystem access, so a command can write shell startup files, `$PATH` executables, or `~/.claude/settings.json` and widen its own access on the next run. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing.md)
- Project config is treated as untrusted for the dangerous switches. `filesystem.disabled` is honored only from user settings, managed settings, and the `--settings` flag, not from `.claude/settings.json` or `.claude/settings.local.json`. Credential `mask` entries, `network.tlsTerminate`, and `credentials.allowPlaintextInject` in those project files are ignored. `permissions.defaultMode` values `"auto"` and `"bypassPermissions"` in project or local project settings do not take effect (`bypassPermissions` there falls back to Manual). — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing.md); [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md)
- Credential handling in Claude Code is sandbox-scoped, not a general output redactor. `sandbox.credentials` can `deny` or `mask` files and env vars for sandboxed Bash only. `mask` shows a sentinel and the sandbox proxy injects the real value on allowed hosts, which requires TLS termination or authentication fails closed. On macOS, file `mask` blocks the file instead of substituting. There is “no built-in credential deny list.” `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is the separate switch that strips credentials from all subprocesses. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing.md)
- Claude Code auto mode’s classifier is described as blocking actions that escalate beyond the request, target unrecognized infrastructure, or appear “driven by hostile content Claude read.” The same page says auto mode reduces prompts but does not guarantee safety, and that it nudges Claude not to stop for clarifying questions unless the prompt or a skill explicitly relies on them. Deny rules, explicit ask rules, `AskUserQuestion`, and critical-path `rm`/`rmdir` still are not blanket-approved. — [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md)
- Compaction loss is an official Claude Code limitation: “When Claude’s context window fills up, compaction summarizes the conversation to free space. This can lose important details.” The documented mitigation is a `SessionStart` hook with matcher `compact`, plus `PreCompact` / `PostCompact` events. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide.md)
- Hook limitations Claude Code states outright: matching hooks run in parallel and a `deny` does not stop sibling hooks, so a logging hook still writes when a guardrail denies. `notify-send` hooks do nothing on headless servers, SSH, and most containers. A `PermissionRequest` hook that allows `ExitPlanMode` cannot clear context and start a fresh implementation session the way the dialog can. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide.md)
- Cursor’s own post states the human-factor failure: as approvals accumulate, users stop inspecting them, worse when several agents run in parallel (“approval fatigue”). The model-side failure they measured internally: agents “repeatedly retry the same terminal command without changing permissions” until tool results name the sandbox constraint and sometimes tell the agent to escalate. Seatbelt is “deprecated in 2016” but still what they use. Linux path filtering cannot be done lazily in seccomp-bpf because the kernel does not hand userspace the path there; remounting ignored files is “the slowest part” of their Linux sandbox. — [Cursor sandbox engineering post](https://cursor.com/blog/agent-sandboxing)
- Cursor’s Seatbelt profile, as published, denies writes to `.vscode`, most of `.cursor` (with an exception for `rules|commands|worktrees|skills|agents`), `.code-workspace`, `.cursorignore`, `.git/config`, and `.git/hooks`. That is an allow-some-config, deny-other-config policy, which is the same class of “workspace config is executable” surface Pillar later attacked via `.claude` hooks. — [Cursor sandbox engineering post](https://cursor.com/blog/agent-sandboxing); [BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/)
- Codex states a structural hole: the sandbox instructions “apply only to the Codex-provided shell tool.” MCP tools are outside that sandbox. Prompt-cache misses they name from production: changing `tools` mid-conversation, changing model (model-specific instructions sit in the cached prefix), changing sandbox/approval/cwd if done by editing an earlier message rather than appending, and an actual bug where MCP tools were not enumerated in a stable order. They also note context exhaustion from “hundreds of tool calls in a single turn,” with compaction as the mitigation, and that compaction replaces the input with a smaller representative list (now including opaque encrypted compaction state). — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Codex keeps requests stateless and does not send `previous_response_id`, “primarily to keep requests fully stateless and to support Zero Data Retention.” The post says this makes the JSON sent over a conversation quadratic, with prompt-cache hits what makes sampling linear. ZDR customers still get prior reasoning via `encrypted_content` because OpenAI keeps the decryption key, not the data. — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Codex instruction loading is capped: AGENTS content from the git root down to cwd is “subject to a limit (32 KiB, by default).” Global scope is `$CODEX_HOME` `AGENTS.override.md` else `AGENTS.md`. Project scope walks directories and can use `project_doc_fallback_filenames`. More specific instructions come later in the prompt. — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Gemini CLI’s own security note: “Sandboxing reduces but doesn’t eliminate all risks.” Documented sharp edges: Windows Low integrity persists on files the sandbox wrote; running the CLI inside Docker and enabling Docker sandboxing requires mounting `/var/run/docker.sock` (the same privileged daemon class named in the escape report); `SANDBOX_FLAGS` can inject arbitrary docker/podman flags, including examples that disable SELinux labeling; GUI apps may not work; default Seatbelt `permissive-open` confines writes but allows broad reads and network. — [Gemini CLI sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- Gemini CLI subagent docs were only seen as a search excerpt, not opened, except where the sandbox page itself is silent on browsers. Not cited.
- Ubuntu 24.04+ AppArmor blocks unprivileged user namespaces, so bubblewrap fails until an admin installs an `unconfined` AppArmor profile for `/usr/bin/bwrap`. Claude Code documents this as a setup step, not a vulnerability, but it is a real deployment failure mode. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing.md)

### Inferences
- Defense in depth that vendors describe is three layers that fail differently: OS sandbox (misses host tools that trust workspace files), permission rules (misses allowlists keyed on command name, and anything the parser cannot see), and a classifier or human prompt (misses approval fatigue, and Claude’s auto mode is explicitly not a guarantee). A project-trust boundary like Claude’s refusal to honor `filesystem.disabled`, credential masks, and `bypassPermissions` from repo settings is part of that stack, not an extra feature.
- Secret handling that is actually documented is “keep credentials out of the sandboxed process,” not “scrub secrets from tool output before it re-enters the model.” General output redaction was not found in the opened pages.
- Prompt caching is a harness constraint, not just a provider discount: Codex will not reorder tools or rewrite the prefix, and will append permission changes instead. Any harness that rebuilds the tool list when an MCP server sends `tools/list_changed` pays a full cache miss. That is a concrete cost/latency failure mode, not a security incident.

### Gaps
- The Pillar Security primary writeups and the GitHub advisories (GHSA-pc9j-3qc2-95wv and others named by BleepingComputer) were not opened. CVE details here are only as BleepingComputer stated them. No CVSS scores were on the opened article.
- The later BleepingComputer piece linked from that article, “Researchers escape OpenAI Codex sandbox to run commands on host,” was not opened. Claims about specific 2026 Codex escapes named Overpatch/Heapjack appeared only in unopened secondary posts and are omitted.
- Incidents in which lab agents reached the public internet (Hugging Face, third-party admin access, and similar) appeared in an unopened wiki-style page. Not used.
- No opened primary page describes a measured incident for prompt injection through tool output as distinct from injection through repo files (README, issue, diff). Claude’s classifier text is the closest official statement (“hostile content Claude read”).
- Background-shell failure modes: a November 2025 Claude Code GitHub issue about `run_in_background` system-reminders burning on the order of a million tokens was in search results only and was not opened.
- Cost accounting, OpenTelemetry attribute names, and per-session `total_cost_usd` were in an unopened podcast page. Not used.
- Whether Cursor’s `.cursorignore` / sandbox deny rules actually stop the CVE-2026-48124 class after 3.0.0 is not something the opened Cursor post (which predates or at least does not mention that CVE) establishes. The changelog date is 17 Feb 2026; the disclosure is 20 Jul 2026; the sandbox post has no visible date.
